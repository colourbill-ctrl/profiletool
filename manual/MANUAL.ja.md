# ICC プロファイルツール — ユーザーマニュアル {#icc-profile-tool-user-manual src=38bba1de}

**ICC プロファイルツール**（ICC Profile Tool、profiletool）は、**ICC.1** および **ICC.2 (iccMAX)** カラープロファイルの検査、検証、ラウンドトリップ編集を行うブラウザベースのツールです。ICC 公式の IccProfLib デモ実装である [iccDEV](https://github.com/InternationalColorConsortium/iccDEV) の WebAssembly ビルドを使い、すべてブラウザ内で動作します。アップロードもインストールも不要です。

**できること：**

- **ヘッダーの閲覧** — 128 バイトのプロファイルヘッダーの全フィールドを、人が読める文字列にデコードして表示します。
- **タグディレクトリの閲覧** — すべてのタグについて、シグネチャ、型、バイトオフセット、サイズ、パディングバイトを表示します。タグをクリックすると型ごとの詳細な説明（iccDEV の `wxProfileDump` の「Describe」ビューと同じ出力）が展開され、対応するタグではインラインの**可視化**も表示されます。トーンレスポンスカーブ、色度図、CLUT 画像と色域画像、名前付きカラーの散布図、さらに単一点の**変換評価機能**です。
- **検証** — ICC Profile Assessment Working Group のチェックリスト（セキュリティ / 適合性 / 品質）を実行します。各チェックには判定が付き、カテゴリーで絞り込めます。
- **ラウンドトリップ編集** — プロファイルを XML または JSON に変換し、内蔵のコードエディターで編集して ICC に戻し、再検証します。保存ボタンで編集後のバイナリをダウンロードできます。
- **プロファイルのチェーン** — **リンク** タブで、プール内のプロファイルを順序付きのチェーンにドラッグし、それを **DeviceLink** に焼き込む、チェーンを通して**画像を変換する**（出力のエンコーディング、圧縮、プレーナー配置、ICC 埋め込みを細かく指定可能）、または**カラーデータセットを変換する**ことができます。
- **HDR の扱い** — プロファイルを ICC.1 の HDR ColorSpace Profile の規則（箇条 8.7.1）に照らしてチェックし、cICP のコードポイントを読み取り、任意のディスプレイヘッドルームでのアダプティブゲインカーブをプロットします。**HDR** タブでは HDR 画像を 1 枚ディスプレイに表示でき、**設定 → 環境** ではこのブラウザとディスプレイで何ができるかを確認できます。
- **chardata から起動** — [chardata](https://chardata.colourbill.com/) で読み込んだプロファイルを、そのままここで開きます。バイト列はブラウザ内で `postMessage` により受け渡されます。
- **URL で起動** — Web 上のプロファイルをツールに指定するリンクを開きます。必要に応じて最初に表示するタブも指定できます（例：`…/profiletool#url=…&tab=VAL`）。

すべてクライアント側で動作します。プロファイルのバイト列がブラウザのタブの外に出ることはありません。

<div class="note">
<strong>ICC.2 (iccMAX) のサポートは部分的です。</strong> ICC.2 プロファイルも ICC.1 と同様に読み込み、検査、検証、ラウンドトリップができます。検証チェックリストには iccMAX 固有のチェックが含まれ、スペクトル PCS やマルチプロセッシングエレメントのタグはデコードされ、変換エンジンは iccMAX の全機能を対象にビルドされています。未対応なのは、マルチパートの <strong>ICS</strong>（Interchange Color Space）ワークフロー、変換適用時の V5 <em>サブプロファイル</em>の選択、一部の ICC.2 プロファイルでの逆探索です。より特殊な ICC.2 機能には未対応の部分があると考えてください。リリースごとに順次対応しています。
</div>

<div class="note">
<strong>HDR ColorSpace Profile のサポートはドラフトに準拠しています。</strong> HDR チェック、<code>headroomAdaptiveGainCurveTag</code> のビュー、HDR タブは、現時点での ICC.1 HDR 改訂版を実装したものです。この改訂版はまだ発行されていないため、発行までに詳細が変わる可能性があります。
</div>

## 1. ワークスペース {#1-the-workspace src=4bc9350f}

profiletool は**複数のプロファイルを扱うワークベンチ**です。ウィンドウは 3 つの部分で構成されます。

- 左側の**プロファイル**ペイン — 読み込んだすべてのものを入れておく*プール*です。
- 右側の**キャンバス** — 上部に **プロファイル**、**比較**、**リンク**、**スペクトル**、**HDR** の 5 つのタブがあります。
- 右端の**設定**ブレード（[設定パネル](#2-settings-panel)を参照）。

### プロファイルの読み込み {#loading-profiles src=2cd0f653}

ファイルは次のどちらかの方法で読み込みます。

- プロファイルペインの上部にある**プロファイルを読み込む**をクリックし、1 つ以上のファイルを選択する。
- ファイルをプロファイルペインに**ドラッグ＆ドロップ**する。

`.icc` / `.icm` プロファイル*だけでなく*画像も読み込めます。**TIFF、PNG、JPEG、HEIC、AVIF** をドロップすると、ツールはその**埋め込み ICC プロファイル**を抽出してプールに追加します。読み取るのはファイルのメタデータだけで、ピクセルは読みません。HEIC と AVIF ではファイルのボックス構造をたどるため、これらの形式を表示できないブラウザを含め、どのブラウザでも動作します。**JPEG XL** ファイルは受け付けません。プロファイルがコードストリーム内で圧縮されており、profiletool はまだその展開に対応していないためです。HEIC と同じコンテナを使う動画やカメラ RAW ファイル（MP4、QuickTime、Canon CR3）は画像として扱われません。**OpenEXR** と **Radiance HDR**（`.hdr`）ファイルは理由を示して拒否されます。どちらの形式にも ICC プロファイルを格納する場所がないためです。OpenEXR は色度座標で、Radiance HDR は任意の `PRIMARIES` ヘッダー行で色を表します。画像を*表示*するには [HDR タブ](#4-7-hdr-tab)を使います。**＋ .cube から新規作成**ボタンでは、`.cube` LUT から DeviceLink を作成できます。結果はプールに追加され、**プロファイル**タブで開かれます。**ICC プロファイルを保存**をクリックするまで何もダウンロードされません。

プロファイルとして受け付けられるのは、先頭 36 バイトに `acsp` シグネチャを含み、IccProfLib の `ValidateIccProfile` で解析できるファイルです。受け付けられなかったファイルは具体的な理由とともに拒否の一覧に表示され、そのバイト列は保持されません。

### プロファイルペイン {#the-profiles-pane src=04750126}

読み込んだプロファイルは、**プロファイルクラス**（Input、Display、Output、DeviceLink、ColorSpace、Abstract、Named Color など）ごとに、折りたたみ可能なセクションにまとめられます。ただし ICC.1 箇条 8.7.1 の **HDR ColorSpace プロファイル**は、一番上の専用セクションに表示されます（ColorSpace クラスのプロファイルなので、ColorSpace セクションから取り出して表示されます）。このセクションは伝達関数によって**リニア伝達関数**と**非リニア伝達関数（PQ、HLG）**に分かれ、各行には伝達関数がバッジで表示されます。この区別は [HDR タブ](#4-7-hdr-tab)で意味を持ちます。OpenEXR や Radiance HDR の画像に割り当てられるのは、リニア伝達関数のプロファイルだけだからです。各行にはファイル名と、クラス、色空間、バージョン、サイズのバッジが表示され、一部しか解析できなかったプロファイルにはフラグが付きます。**A–Z** ボタンで並べ替え順を切り替え（読み込み順 → 昇順 → 降順）、行の **×** で削除し、ペイン右端のハンドルで幅を変更できます。ペイン全体を折りたたむこともできます。

行をクリックすると選択され、Ctrl/Cmd+クリックで選択の切り替え、Shift+クリックで範囲選択ができます。**行をプールからタブへドラッグ**すると、そのタブで使えるようになります。

<div class="note">
<strong>プールはそのセッション限りです。</strong> 何もアップロードされず、何も保存されません。永続的な保存先はあくまでお使いのファイルシステムです。ページを再読み込みするとプールは空になります。
</div>

### タブ {#the-tabs src=034c9677}

| タブ | 機能 |
|---|---|
| **プロファイル** | **1 つ**のプロファイルを検査します（ヘッダー、タグ、検証、分析、XML、JSON）。ここに新しいプロファイルをドロップすると、現在のプロファイルと置き換わります。 |
| **比較** | **2 つ以上**のプロファイルの色域を重ねて表示します。 |
| **リンク** | プロファイルをチェーンにして DeviceLink を作成するか、それを通して画像 / データセットを変換します。 |
| **スペクトル** | 単一チャンネルのスペクトル画像を 1 つのマルチチャンネル TIFF にまとめます。 |
| **HDR** | **1 枚**の HDR 画像をディスプレイに表示し、SDR ↔ HDR を切り替えられます。[HDR タブ](#4-7-hdr-tab)を参照してください。 |

スペクトルタブと HDR タブは、プール内のプロファイルではなく画像ファイルを直接受け取ります。その他の各タブはそれぞれ独自のプロファイルの組を持ち、それらはタブストリップの下に削除可能なチップとして表示され、タブ自体には件数のバッジが付きます。最初に読み込んだプロファイルは自動的に**プロファイル**タブで開かれます。それ以降は、プールから目的のタブへドラッグしてください。ファイルを直接タブにドロップすると、プールへの読み込み*と*そのタブへの配置が一度に行われます。

<div class="note">
<strong>サイズ上限：</strong>256 MB を超えるファイルは読み込まれません。実際のプロファイルは通常 10 MB を大きく下回ります。この上限は、悪意のあるドロップや postMessage によってタブの WASM ヒープが使い果たされるのを防ぐためだけのものです。
</div>

## 2. 設定パネル {#2-settings-panel src=3bf599d9}

画面右端の **⚙** ボタン（モバイルでは右上の歯車アイコン）をクリックすると設定が開きます。パネルはコンテンツの大きさを変えずに、その上にスライドして表示されます。

⚙ の下には、さらに 2 つのボタンがあります。

- **?** はこのガイドを**アプリ内で**、ウィンドウの上にスライドインするペインとして開きます。ヘッダーには検索ボックスがあり、入力すると一致箇所がハイライトされます。`Enter` / `Shift+Enter`（または `˄` `˅` ボタン）で一致箇所を順に移動でき、`Escape` で検索をクリア、もう一度 `Escape` を押すとペインが閉じます。
- **✉** は colourbill.com のお問い合わせフォームを新しいブラウザタブで開きます。

パネルには**表示**と**環境**の 2 つのグループがあります。パネルの幅は左端をドラッグして変更でき（220–560 px）、その幅は記憶されます。

### 背景 {#background src=1450fe76}

アプリのテーマを**ライト**、**ダーク**、**システム**（OS の設定に従う）から選びます。選択はセッションをまたいで保持されます。**システム**モードでは、アプリが `prefers-color-scheme` を監視し、OS のテーマが変わると自動的に切り替わります。ライトまたはダークを明示的に選ぶと、この監視は解除されます。

### 数値形式 {#number-format src=af65622c}

プロファイルビュー全体での数値の表示方法を、**16 進数**または **10 進数**から選びます。

### 言語 {#language src=38c60535}

インターフェースの言語を指定します。**システム既定 (…)** はブラウザのロケールを検出し、対応言語のうち最も近いものを使います。括弧内にはその言語の自言語名が表示されるので、どの言語が選ばれたかがわかります。翻訳の対象はアプリの UI 部分です：プロファイルペイン、タブのラベル、リンク・スペクトル・HDR の各ツール、タグ内の HDR ゲインカーブのビュー、環境とその理由表示を含む設定パネル、このガイドの UI 部分。翻訳されないテキストもあります。
- IccProfLib が生成する文字列（タグの説明、検証メッセージ、ヘッダーのフィールド名）は、C++ ライブラリから英語のまま出力されます。
- ブラウザフラグの名前は、ブラウザ自身のフラグページと一致するよう英語のままです。
- 環境パネルの**ディスプレイイベント**（Display events）のログは、そのままバグ報告に貼り付けられるよう英語のままです。
- このガイドも同じ設定に従いますが、HDR のセクションは例外です。HDR サポートはベータ版で本文がまだ変わり続けているため、英語のままです。また、翻訳の最終更新以降に英語版が改訂されたセクションも、翻訳が追いつくまで注記付きで英語で表示されます。

対応言語：English、Français、Deutsch、Italiano、Español、Português (PT)、Português (BR)、Svenska、中文（简体）、中文（繁體）、日本語、한국어。chardata の設定パネルも同じ言語に対応しているため、一方のアプリで言語を切り替えると、もう一方でも一貫した表示になります。

### 環境 {#environment src=2eb1ea2c}

**この**ブラウザ、プラットフォーム、ディスプレイで何ができるかを表示します。形式や HDR 機能が使えないときに、その理由を確認できます。上から順に：

- **概要** — ブラウザとオペレーティングシステム、およびディスプレイが HDR を報告しているかどうか。
- **ブラウザのフラグ**（Chrome、Edge、Opera、Brave）— *Experimental Web Platform features* が有効かどうか。このフラグは HDR キャンバスを有効にし、ページがディスプレイの HDR ヘッドルームを読み取れるようにします。
  - フラグが無効だと判明している場合は、ボックスがハイライトされます。このブラウザで使用できる WebGPU がない場合は、HDR キャンバスが HDR を描画する唯一の手段となるため**必須**と表示されます。それ以外の場合は**任意**です。
  - プロファイルの検査には一切必要ありません。
  - Web ページからブラウザのフラグを開いたり変更したりすることはできません。**コピー**をクリックし、そのアドレスをアドレスバーに貼り付け、フラグを *Enabled* に設定してから、ブラウザを再起動してください。
- **ディスプレイ情報** — **HDR ディスプレイ**、**広色域**（sRGB、Display P3、Rec. 2020）、**ピクセル比**、および使用中の **HDR キャンバス経路**（`float16-canvas`、`webgpu`、またはなし）。条件の異なる画面へウィンドウをドラッグすると、これらは自動的に更新されます。切り替わるのは、ウィンドウの大部分が新しい画面に移ったときです。
- **ディスプレイを識別**（Chromium 系ブラウザ）— ウィンドウがどのモニター上にあるかを確認する許可を求めます。許可すると、見た目の似たモニター間でもパネルが更新され、**現在のモニター**の名前と、ブラウザが公開している場合（上記のフラグを有効にした Chrome）は **HDR ヘッドルーム**が表示されます。例：*1.35 段（≈ SDR 白の 2.55 倍）*。許可を拒否した場合は、サイトの設定で変更してください。
  - ヘッドルームは SDR 白より上の余裕なので、ノートパソコン内蔵の HDR パネルでは**輝度を上げると小さくなり**（SDR 白が明るくなる一方、パネルのピークは変わらないため）、輝度を下げると大きくなります。HDR を見るときは輝度を下げてください。
  - Windows では、輝度を変更してから数秒後、ディスプレイドライバーが値を報告した時点で新しい値が反映されます。ウィンドウが別の画面に移動したときや、Chrome が再びアクティブなアプリになったときにも更新されます。
- **ディスプレイイベント** — 直近 20 回の更新と、それぞれのきっかけを記録した折りたたみ式のログです。ディスプレイの問題を報告するときに役立ちます。
- **形式の表** — 形式ごとに 1 行（ICC プロファイル、TIFF、PNG、JPEG、OpenEXR、Radiance HDR、AVIF、HEIC/HEIF、JPEG XL）で、次の 3 つの問いに答えます：
  - **検査**：埋め込みプロファイルを読み取れるか。
  - **表示**：ピクセルを表示できるか。
  - **HDR**：白より明るく描画できるか。

  ✕ の理由は、行にポインターを重ねると表示されます。表示できない形式は、表の下に理由とともに一覧表示されます。ドットの付いた形式は profiletool 自身がデコードするもので、どのブラウザでも同じように動作します。**検査**は、プロファイルがコードストリーム内で圧縮されている JPEG XL を除き、すべての形式で ✓ です。

## 3. プロファイルビュー {#3-profile-views src=ccf59d34}

プロファイルを検査するには、プールから**プロファイル**タブへドラッグします。タブの上部には、ファイル名と **ICC プロファイルを保存** ボタン（編集後は *● 変更あり — 未保存* のピルも）を表示するバーがあり、その下にビューアーがあります。ビューアーにはタイトルバー（ファイル名 · バイト単位のサイズ · IccProfLib のバージョン · 有効性バッジ）と独自のタブストリップがあります。

バッジは**検証**レポートの要約です：失敗や警告のチェックが 1 つもなければ緑の**合格**、警告のチェックが 1 つ以上あれば黄色の**警告**、失敗したチェックが 1 つでもあれば赤の**不合格**です。

<div class="note">
<strong>一部しか解析できなかったプロファイル：</strong>プロファイルの損傷が大きく、バリデーターが構造しか読み取れない場合は警告バナーが表示され、<strong>ヘッダー</strong>と<strong>タグ</strong>のタブだけが使えます。検証、分析、XML、JSON は非表示になります。そのプロファイルを適用してはならないためです。
</div>

### 3.1 ヘッダー {#3-1-header src=45c71bd0}

ICC プロファイルの 128 バイトのバイナリヘッダーの全フィールドを 2 列の表で表示します。値は IccProfLib の `CIccInfo` を使って人が読める文字列にデコードされます（シグネチャの展開、日付の整形、固定小数点値の変換）。**プロファイル ID**（ヘッダー内の MD5 ハッシュ）は、上部のハイライトされた帯に表示されます。

### 3.2 タグ {#3-2-tags src=90f22730}

プロファイルのタグディレクトリにあるすべてのタグを 6 列のグリッドで表示します。

| 列 | 意味 |
|---|---|
| `#` | ディレクトリ内の位置（1 から始まる） |
| `Name` | 人が読める長い名前（例：`profileDescriptionTag`） |
| `ID` | 4 文字のシグネチャ（例：`desc`） |
| `Offset` | ファイル先頭からのバイトオフセット |
| `Size` | タグデータのバイトサイズ |
| `Pad` | このタグと次のタグの間のパディングバイト |

タグの**型**シグネチャ（例：`descType`、`mft2`、`mAB`）は、展開したタグの上部にオフセットとサイズとともに表示されます。

タグはオフセット順に並びます。**パディング**列は色分けされ、`Pad < 0`（タグの重なり、規格非準拠）は赤、`Pad > 3`（仕様を超えるパディング）は黄色で表示されます。

**行をクリック**すると、その場で展開されます（アコーディオン形式で、一度に開けるタグは 1 つ）。展開した詳細の最後には、必ず型ごとの完全な説明が表示されます。これは IccProfLib の `CIccTag::Describe(verbosity = 100)` を実行した結果と同じです。大きな CLUT やカーブを含むタグ（例：`A2B0`、`B2A0`）では、すべてのグリッドセルやカーブ点が含まれます。

その説明の上には、可視化できるデータを持つタグについて、1 つ以上の**インライン可視化**が、それぞれ折りたたみ可能なセクションとして表示されます。

| タグの種類 | 可視化 |
|---|---|
| トーンカーブ（`rTRC`/`gTRC`/`bTRC`/`kTRC`） | トーンレスポンスカーブを恒等直線とともにプロットします。カーブ表はその下に折りたたまれています。 |
| RGB 色材（`rXYZ`/`gXYZ`/`bXYZ`）と白色点（`wtpt`） | 該当する原色（または白色点）をハイライトした CIE 1931 色度図。色材 / 白色点のデータはその下に表示されます。 |
| LUT 変換（`A2B0–3`、`B2A0–3`、`gamt`、`pre0–2`） | 入力側と出力側のトーンカーブ（重ねて表示し、色材ごとに色分け。凡例で各トレースの表示を切り替え可能）、画像化した CLUT 格子、**色域画像**（プロファイルの `gamutTag` 用。ニュートラル = 色域内、赤 = 色域外で色分け）、**評価機能**（後述）、折りたたまれた生データの表。 |
| 名前付きカラー / 色材テーブル（`ncl2`/`nmcl`/`clrt`/`clot`） | CIELAB a\*b\* 図（および CIE xy 図）上の色の散布図。テーブルはその下に折りたたまれています。 |
| 符号化非依存コードポイント（`cicp`） | **コードポイント**：色の原色、伝達特性、マトリクス係数、フルレンジフラグを、それぞれ ITU-T H.273 の定義どおりの名前で表示します。H.273 で割り当てられていない値や、ゼロでない予約バイトにはフラグが付きます。 |
| アダプティブゲインカーブ（`headroomAdaptiveGainCurveTag`） | **指定ディスプレイヘッドルームでのゲイン**と、タグが代替画像を保持している場合は**ゲインカーブ**。後述の *HDR gain curves (HAGC)* を参照してください。 |

<div class="note">
<strong>不正なデータも隠しません。</strong> カーブなどの可視化要素が IccProfLib の検証に通らない場合（例：ガンマが 0 に縮退したトーンカーブ）でも、グラフを黙って省略するのではなく、描画できる部分を描画し、ライブラリが示す正確な理由とともに ⚠ 警告を表示します。
</div>

#### 変換の評価機能 {#the-transform-evaluator src=c70f94b4}

LUT 変換（`A2B*` / `B2A*` / プレビュータグ）では、**評価**セクションで、そのタグの変換を指定した単一の色に適用できます。外部のカラーエンジンは使わず、IccProfLib を直接使います。方向はタグに従い（`A2B*` はデバイス → PCS、`B2A*` は PCS → デバイス）、レンダリングインテントもタグで決まります（`…0` は知覚的、`…1` は相対比色、`…2` は彩度）。

- 入力は**浮動小数点**値（デバイスチャンネル、または人が読める Lab/XYZ 単位の PCS）で指定するか、タグに CLUT がある場合は**グリッド点**のインデックス（格子上のノード位置）で指定します。
- 出力は、内部の正規化された 0–1 エンコーディングと、人が読める単位（PCS の結果なら Lab/XYZ）の**両方**で表示されます。

色域タグ（`gamt`）には評価機能はありません。可逆な変換ではなく、1 チャンネルの色域内 / 色域外マップだからです。代わりに色域画像が表示されます。

### 3.3 検証 {#3-3-validation src=b72d6c69}

読み込んだプロファイルに対して **ICC Profile Assessment Working Group** のチェックリストを実行し、レポートとして表示します。チェックは iccDEV の `iccPawgReport` ツールに由来し、別の WebAssembly モジュールとしてコンパイルされていて、このタブを初めて開いたときにだけ取得されます。（同じレポートがタイトルバーの有効性バッジにも使われ、URL 起動では `VAL` または従来の `PAWG` で指定できます。）

各チェックは**セキュリティ**、**適合性**、**品質**のいずれかに分類され、それぞれ 1 つの判定を持ちます。HDR コンテンツを含むプロファイルには、4 つ目のグループ **HDR** が加わります。その最初のチェックは、プロファイルが ICC.1 に適合する **HDR ColorSpace プロファイル**（箇条 8.7.1）かどうかを報告し、残りのチェックはこの箇条が依拠する HDR メタデータを確認します。

| 判定 | 意味 |
|---|---|
| **合格 (PASS)** | チェックに成功しました |
| **警告 (WARN)** | 確認が望ましい、致命的ではない懸念事項です |
| **不合格 (FAIL)** | プロファイルがチェックを満たしていません |
| **ギャップ (GAP)** | チェックを完全には評価できませんでした（例：未実装） |
| **該当なし (N/A)** | このチェックはこのプロファイルに適用されません |
| **未実行 (NOT RUN)** | チェックはスキップされました |

上部の要約行には、各判定の件数が色付きのピルで表示されます。**ピルをクリックすると**下のレポートを絞り込めます。青いハローは現在表示中のカテゴリーを示し、件数がゼロのピルは無効になります。たとえば **合格 (PASS)** と **該当なし (N/A)** をオフにすると、警告と不合格だけに集中できます。

### 3.4 分析 {#3-4-analysis src=9478bc94}

プロファイルのカラー変換から導き出す、プロファイル全体の品質分析です。専用の WebAssembly モジュール（iccDEV の可視化エンジン）で計算され、このモジュールはこのタブを初めて開いたときにだけ取得されます。結果はアプリ独自のスタイルでプロットされます。

各分析は折りたたみ可能なセクションで、**最初はすべて閉じています**。これは意図的なものです。どのセクションもプロファイル全体に対する変換処理を 1 回分必要とするため、タブを切り替えた瞬間に 6 つの分析が一斉に走るのではなく、開くかどうかを明示的に選べるようにしています。結果はキャッシュされるので、セクションを開き直すと即座に表示されます。読み込んだプロファイルに該当しないセクションには、代わりに短い*該当なし*の注記が表示されます（たとえば matrix/TRC のディスプレイプロファイルには、分析対象となるデバイス↔PCS の CLUT がありません）。

#### プロファイル統計 {#profile-statistics src=f2d4f2db}

**1 つ**の選択したレンダリングインテントについて、プロファイル全体の指標を表示します。2 つのリストボックスと 1 つのチェックボックスで操作します。

- **レンダリングインテント** — 知覚的 / 相対比色 / 彩度 / 絶対比色。
- **ラウンドトリップの種類** — 報告する精度指標（後述）。
- **MPE（カラー）タグを使用** — オフでは測色用のルックアップテーブルを、オンではマルチプロセッシングエレメント / カラータグを使います。色域内の概要には影響しないため、その場合は無効になります。

表には、**色域体積**（ΔE\*ab³ 単位。デバイス → PCS の `A2B` 変換が囲む体積で、境界をボクセル化して内部のセルを数えて測定）と、選択したラウンドトリップの**最小 / 平均 / 標準偏差 / P90 / 最大** ΔE\*ab が並んで表示されます。その下には ΔE 分布のヒストグラム（相対度数の棒グラフと累積度数の折れ線）があり、さらに誤差が最大となる `L, a, b` と、PRMG の場合はプロファイルが Perceptual Reference Medium Gamut を示しているかどうかが表示されます。

4 種類のラウンドトリップ：

- **色域内の概要 (RT0)** — デバイス値のグリッドを PCS へ変換し、デバイスへ戻し、再び PCS へ変換して、2 回の PCS 値の間で ΔE\*ab を測定します。高速な色域内の安定性チェックです。
- **反転 + 色域 (RT1)** — 各デバイス色の PCS 値と、Lab → デバイス → Lab のラウンドトリップを 1 回行った後の PCS 値との ΔE\*ab。反転の精度*と*色域マッピングの両方を反映します。
- **再現性 (RT2)** — 1 回目と 2 回目のラウンドトリップの間の ΔE\*ab。1 回目の色域クリッピングとは無関係に、ラウンドトリップを繰り返したときの安定性を示します。
- **PRMG 相互運用性** — Perceptual Reference Medium Gamut 内の PCS 色を 1 回ラウンドトリップさせます。その ΔE 分布が、プロファイル間の相互運用性を示します。

ヒストグラムの下にある**明度別のラウンドトリップ ΔE** は、要約値では答えられない問い、つまり反転がトーンスケールの*どこで*うまくいっていないのか、そして問題が*色域のどこまで内側に*及んでいるのかに答えます。

32 段階の明度をサンプリングします。各明度で**色域境界上**の 64 点を取り、それらを中性軸に向けてクロマの 80 %、50 %、20 % まで縮めた点でも繰り返します。合計 8,192 点をそれぞれ個別にプロットし、明度レベルの間は点線で区切ります。

帯ごとに読んでください。1 つの帯の中では、点が左の色域表面から右のニュートラルへ並ぶため、誤差は帯の中で**下がっていく**はずです。境界付近の色は最も反転が難しく、ニュートラル付近の色は最も容易です。ニュートラルまで誤差が高いままの帯は、その明度でプロファイルに問題があることを意味します。最も高いスパイクは、色域境界そのものの反転が最もうまくいっていない明度レベルを示します。

すべてのシードは構成上色域内にあるため、見えているのは到達できない色がクリップされた結果ではなく、`B2A`/`A2B` の本当の不一致です。このプロットは**独自の**サンプリング（意図的に色域境界寄りに重み付け）を使うため、その平均と最大は上の表より高くなり、表とは比較できません。レンダリングインテントの選択には従いますが、ラウンドトリップの種類には従いません。

指標に必要なデバイス↔PCS 変換を持たないプロファイルには*該当なし*の注記が表示されます。サンプリングするには広すぎるデバイス空間は、エラーではなくスキップとして報告されます。

#### 極値の測色 {#extrema-colorimetry src=be6c9597}

プロファイルの再現範囲の両端、つまり印刷オペレーターが通常まず確認する数値です。

- **白色点** — **色材ゼロ**、つまり素地そのものの色。
- **黒色点** — PCS の黒（L\*=0、a\*=b\*=0）を選択した `B2A` テーブルに通して、プロファイルが黒として*選ぶ*インキングを求め、そのインキングを `A2B1` で読み戻して求めます。
- どちらも**相対**と**絶対**の測色値で表示されます。絶対は素地そのものの色を示し（青みがかった白い紙なら L\* 95、b\* −4 のような値になります）、相対は完全な白を基準に参照し直した値です。2 つの列が同じでも正常です。メディアの白が光源と一致しているだけです。メディア白色点タグのないプロファイルでは、相対のみが表示されます。
- **黒色点でのインキング**と **TAC** — その黒における各チャンネルのインキ量と、その合計である総面積率（インキ制限の値）です。

`B2A` テーブルはそれぞれ独自に黒のインキングを選ぶため、黒色点はインテントによって実際に異なります。レンダリングインテントのセレクターがあるのはそのためです。

その下の**ベタとクロマ最大点**は、各インキのコーナー（C、M、Y、R、G、B、K）について、色相 / クロマ / 明度のどこに到達するかと、素地からそこへ向かう途中で見つかった最もクロマの高い点を示します。これらの行は `A2B1` を通して測定されるため、**インテントのセレクターでは変わりません**。素直なプロファイルでは 2 つの行が一致します。ベタより*前に*クロマ最大に達した場合は、その行にフラグが付きます。その点を過ぎると、インキを増やしてもクロマは上がらず、暗くなるだけだからです。

**出力（プリンター）プロファイルのみ** — この分析は、色材ゼロ = 素地であることを前提としています。色相ごとの表には、さらに **CMYK または CMY** のデバイス空間が必要です。n 色（nCLR）プロファイルはチャンネルを任意の順序で命名するため、どのチャンネルが「シアン」かを判別できません。その場合、表は推測せずにその旨を報告します。

#### 中立軸インキング {#neutral-axis-inking src=aa5449e4}

中性軸（a\*=b\*=0）を白（L\*=100）から黒（L\*=0）まで、プロファイルの `B2A`（PCS → デバイス）テーブルを通してスイープし、その間にプロファイルが各デバイス色材をどれだけ置くかをプロットします。古典的な GCR / ニュートラルビルドのカーブです。デバイスチャンネルごとに 1 本のカーブを、色材ごとに色分けして表示します。

分版の上には、さらに 1 本のカーブが描かれます：

- **L\* 出力（トーン）** — トーンレスポンス、つまりプロファイルをラウンドトリップした後に中性軸が実際にどの明度に着地するかです。その形から 2 つのことが読み取れます。対角線より下にたわんでいれば、グレーは指定より暗く再現されます。さらに有用なのは、カーブが**プロファイルが到達できる最も暗い明度で平坦になる**ことです。この平坦部*こそが*メディアの黒色点であり、上の「極値の測色」セクションの値と一致するはずです。

**出力（プリンター）プロファイルのみ**。その他のプロファイルクラスでは注記が表示されます。

#### シャドウ部のインキ使用量 {#ink-usage-in-shadows src=e62016b7}

意図的に暗くした一定の明度で、a\*b\* 平面を横切る 4 本の直線経路（0°、45°、90°、135°）を選択した `B2A` テーブルに通し、得られた分版をそれぞれプロットします。

経路上のすべてのサンプルが同じ L\* を持つため、色材に急な段差や反転があれば、それは色相とクロマの処理だけに起因します。これはシャドウ部の色域マッピングのアーティファクトの特徴であり、印刷では暗部のバンディングや急な色ずれとして現れる類のものです。経路は色域のはるか外側から色域を通り抜けて反対側の外まで伸びるので、プロファイルがどこでクランプし始めるかもわかります。

明度の平面は自動的に選ばれます。プロファイルのブルーのコーナーと、C、M、Y、R、G のうち最も暗いものとの中間です。知覚的テーブルと彩度テーブルでは、まず明度をメディアの黒色点から PCS の黒まで引き伸ばします（これらのテーブルはそこに黒があることを前提としているためです）。セクションには、補償後の平面と元の平面の両方が表示されます。

**出力（プリンター）プロファイルのみ**で、上の色相ごとの表と同じ CMYK/CMY の制限があります（平面はインキのコーナーから導き出されるため）。

#### 中性軸を通る一次色インキ経路 {#primary-inking-paths-through-neutral src=cb510c25}

3 本の経路（シアン→レッド、マゼンタ→グリーン、イエロー→ブルー）は、それぞれ一方の原色コーナーから、両端点の中間の明度で**中性軸を通って**反対側のコーナーへ向かいます。各経路を選択した `B2A` テーブルに通し、分版としてプロットします。

これは「シャドウ部のインキ使用量」の色域内版です。あちらでは経路が意図的に色域外を通り、色域マッピングのアーティファクトをあぶり出しますが、こちらでは**すべてのサンプルが構成上色域内にあります**。両端点はプロファイル自身の原色で、ピボットは中性軸上にあるからです。したがって、これらの経路上で色材に段差、折れ、反転があれば、それは色域クリッピングのせいではなく、CLUT の滑らかさの欠陥です。ニュートラルのピボットは各プロットの中点にあり、そこではバランスの取れたニュートラルビルドが見えるはずです。

知覚的テーブルと彩度テーブルでは、「シャドウ部のインキ使用量」とまったく同じように、明度がインテントに合わせて黒点補償されます。

**出力（プリンター）プロファイルのみ**で、同じ CMYK/CMY の制限があります（コーナーは色相ごとの表と同じソースから得られるため）。

#### インキ使用量の統計 {#ink-usage-statistics src=191fd7cd}

プロファイルが各色材をどれだけ置くかを、平均被覆率と**全体に占める割合**で示します。分版のインキ消費の特徴を表すものです。

表は中性軸全体で各色材を合計し、その平均被覆率と、置かれた全インキに対する割合を報告します。診断に役立つのは割合の列です。これはプロファイルのニュートラルビルドの指紋のようなもので（シアンの多いグレーバランスとブラックの多いグレーバランスでは値が異なります）、サンプル数にも依存しません。

2 つ目の表である**色域上および色域内のすべての色**にわたるインキ使用量は、*保留中*として表示されています。まだ実装されていない色域境界の構築が必要なためです。

**出力（プリンター）プロファイルのみ。**

#### CLUT 画像 {#clut-image src=a3fec568}

デバイス↔PCS 変換のカラールックアップテーブルを画像としてタイル表示します。どのレンダリングインテントのテーブルを表示するかを選ぶセレクター（`A2B0`–`A2B3`、`B2A0`–`B2A3`、プレビューテーブル）があります。テーブルの構造的な破損をひと目で見つけるのに役立ちます。ズーム、パン、リセットはキャンバス上のコントロールで行います。

**`B2A`（PCS → デバイス）テーブル**を選ぶと、格子の下に**色材ごとのインキ被覆率画像**がグレースケールで表示されます。インキごとの分版で、暗いほどそのインキが多いことを示します。セクションは `A2B` テーブル（出力はインキではなく L\*a\*b\*）を表示した状態で開くため、セクション上部のヒントでこれらの画像を案内しています。単純なカラープレビューができない **n 色（nCLR）出力**（5 色、6 色、7 色）では、メイン画像が**プロファイルの順方向 `A2B` でカラーマネジメント**されるため、単一チャンネルのグレーではなく実際の色で描画されます。

#### 色域画像 {#gamut-image src=92f58c0f}

色域タグの色域内 / 色域外マップです。PCS の色が再現可能な箇所はニュートラル、デバイスの色域外にある箇所は赤で表示されます。プロファイルに `gamt` タグがある場合にのみ表示されます。

### 3.5 XML {#3-5-xml src=dfd43c4e}

プロファイルを XML に変換し（iccDEV の `iccToXml` CLI と同じライターである IccLibXML を使用）、シンタックスハイライト付きの CodeMirror エディターで表示します。XML を編集して **ICC に変換** をクリックすると、バイナリに戻せます。ビューアーが再検証し、プロファイルタブのバーにある **ICC プロファイルを保存** ボタンで結果をダウンロードできます。

エディターのテキストが最後の変換出力と異なると**未保存**のインジケーターが表示されるので、編集が反映済みかどうかがひと目でわかります。変換に失敗した場合は、IccLibXML の解析エラーが問題のある行 / 列とともにエディターの上に表示されます。

### 3.6 JSON {#3-6-json src=59c3f2e5}

XML タブと同じ考え方ですが、バリデーターのラッパー（`json-wrapper.cpp`）が生成するプロファイルの JSON 表現を使います。編集し、**ICC に変換** をクリックして保存します。JSON 形式はよりコンパクトでスクリプトから扱いやすく、XML 形式は iccDEV の CLI ツールを使ったことがあれば馴染みがあるでしょう。

## 4. リンクタブ {#4-combine-tab src=735d6198}

profiletool は、読み込んだすべてのプロファイルを左側の**プロファイルプール**に保持します。上部には 5 つのタブ、**プロファイル**（前述の単一プロファイルビューアー）、**比較**、**リンク**、**スペクトル**、**HDR** があります。**リンク** タブでは、プロファイルをチェーンにつないで活用します。チェーンから **DeviceLink** を作成したり、チェーンを通して**画像を変換**したり、**カラーデータセットを変換**したりできます。

### 4.1 チェーンの構築 {#4-1-building-a-chain src=83ab772c}

プールから 1 つ以上のプロファイルをリンクパイプラインのカードにドラッグすると、順番にチェーンへ追加されます。チェーンは**縦方向のスタック**で、ソースが上、シンクが下です。各プロファイルは**変換 1 つ**を担い、ツールはそこに入る色空間と出る色空間（例：`RGB → Lab`）を表示し、段と段の間の線には**接続空間**がラベル表示されます。エンジンはチェーン全体をリアルタイムで検証し、端から端までの流れ（例：*チェーン：RGB → CMYK*）を報告するか、接続できない箇所を段ごとに説明します。

- 段の**並べ替え**は、グリップ（`⠿`）をドラッグするか ▲ / ▼ ボタンで行います。× で削除します。
- **方向の反転** — 先頭の変換の ⇅ ボタンでチェーンの方向が反転し、後続の段にも順に反映されます。
- **レンダリングインテント** — *レンダリングインテント（すべて）* でチェーン全体に 1 つを選ぶか、各段のリストボックスで個別に上書きします。どちらのコントロールもポインターを重ねると、選択中のインテントの説明が表示されます。4 つの基本インテントに加えて、必要なテーブルを持つプロファイルでは *no D2Bx/B2Dx* と *+ BPC*（黒点補償）のバリエーションも選べます。

<div class="note">
<strong>チェーン内の HDR ColorSpace プロファイル。</strong> ICC.1 の HDR ColorSpace Profile には TRC タグがありません（箇条 8.7 は ColorSpace プロファイルに TRC タグを定義していません）。そのため、これを通る変換には <code>AToB0Tag</code> が使われます。このテーブルは、HDR 処理を持たないソフトウェアのために箇条 8.7.1.5 が要求する HDR&#8594;SDR レンダリングです。チェーンに HDR ColorSpace Profile が含まれる場合は、カードにその旨が表示されます。作成される DeviceLink、画像、データは、プロファイルの HDR の振る舞いではなく、この SDR フォールバックを反映したものになります。
</div>

### 4.2 DeviceLinkを作成 {#4-2-make-devicelink src=2cb72a0d}

チェーン全体を 1 つの **DeviceLink** プロファイルに焼き込みます（iccDEV の `iccApplyToLink` をブラウザに移植したもの）。名前を付けて **DeviceLinkを作成** をクリックすると、結果は他のプロファイルと同様にプールとリンクのアキュムレーターに追加され、プロファイルタブで検査したり、別のチェーンで再利用したりできます。

### 4.3 画像を変換 {#4-3-transform-image src=461fcd83}

画像スロットにラスター画像（TIFF、PNG、JPEG）を 1 つドロップし、**画像を変換** をクリックすると、チェーンを通して変換されます（`iccApplyProfiles` をブラウザに移植したもの）。画像はまずヘッダーだけを調べて検証され、その色空間がチェーンの入力と一致している必要があります。結果は**ダウンロード**されます。画像がプールに保存されることはありません。

有効な画像が読み込まれると **画像出力オプション** パネルが表示され、`iccApplyProfiles` CLI に対応する出力側の設定が並びます：

- **エンコーディング** — *元と同じ*、8 ビット、16 ビット、**浮動小数点（32ビット）**。
- **圧縮** — なし、**LZW**、**ZIP**（Deflate）。
- **プレーナー** — **コンポジット**（チャンキー）または**セパレート**のプレーン。
- **CMM補間** — **四面体**または**線形**。
- **ICCを埋め込む** — チェーンの最後の（出力空間の）プロファイルを出力にタグ付けします。

既定では RGB/グレーの出力は PNG のままです。TIFF 専用の設定（浮動小数点、LZW/ZIP、セパレートプレーン）を選ぶと、コンテナが TIFF に切り替わります。

<div class="note">
<strong>埋め込みプロファイル：</strong>ドロップした画像に ICC プロファイルが埋め込まれている場合は、それを<strong>抽出</strong>するよう促すバナーが表示されます。ワンクリックで、プロファイルがプールに追加され、チェーンの先頭（ソース空間）に配置されます。
</div>

### 4.4 データを変換 {#4-4-transform-data src=96934eec}

データスロットにカラーデータセット（CGATS/IT8、CSV、CxF、JSON）をドロップし、**データを変換** をクリックすると、すべてのパッチがチェーンを通して変換されます（`iccApplyNamedCmm` 相当）。ツールはデータセットに含まれるデータの種類（デバイス / Lab / XYZ / スペクトル）を読み取り、チェーンの入力に必要なものを渡します。**スペクトル**入力は、選択した**観測者**と**光源**を使い、iccDEV の標準の計算器で測色値に変換されます。重複パッチは除外できます（中央値または平均値）。結果は表で開かれ、CSV として**保存**できます。

### 4.5 観察者の変更 {#4-5-observer-change src=738ba4d4}

リンクタブには**2 つ**のメーカーカードがあります。リンクパイプラインの上にある **観察者の変更** カードは、V5 RGB ディスプレイプロファイルと V5 観測者（PCC）プロファイルから、v4.3 の matrix/TRC ディスプレイプロファイルを作成します。両方をカードにドラッグすると、プロファイルクラスに応じて **V5 RGB ディスプレイ** と **V5 オブザーバー (PCC)** のスロットに自動的に振り分けられます。次に **V4 ディスプレイプロファイルを作成** をクリックし、名前を付けて **作成** をクリックします。結果はプールとこのタブに追加されます。どちらにも当てはまらないプロファイルは、警告とともに無視されます。

### 4.6 比較タブとスペクトルタブ {#4-6-compare-and-spectral-tabs src=b934d7e3}

**比較** タブは、プール内の 2 つ以上のプロファイルの色域境界を重ねて表示し（3D シェルと 2D の明度スライス）、どこが違うかを確認できます。プロファイルが HDR ColorSpace Profile の場合は **SDR フォールバックを表示中** という注記が表示され、各色域がプロファイルの HDR レンジではなく `AToB0Tag` の SDR レンダリングから構築されていることを説明します。HDR レンジは有界な PCS では描画できないためです。**スペクトル** タブは、単一チャンネルのスペクトル画像のセット（チャンネル順にドロップ）を 1 つのマルチチャンネル TIFF にまとめます（`iccSpecSepToTiff`）。

## 5. ラウンドトリップ編集 {#5-round-trip-editing src=595f380b}

XML タブと JSON タブは、どちらもプロファイルを ICC バイナリに書き戻せます。典型的な手順は次のとおりです：

1. ICC プロファイルを**読み込みます**。
2. **XML** または **JSON** タブを開きます。**XML に変換** / **JSON に変換** をクリックしてエディターに内容を表示します。
3. ページ内のエディターで**編集**します。ツールバーの横に未保存のインジケーターが表示されます。
4. **ICC に変換** をクリックします。ラッパーが新しいプロファイルを生成し、検証を再実行して、ヘッダー / タグ / 検証の各タブを更新します。
5. プロファイルタブのバーで、ファイル名の横に **● 変更あり — 未保存** のピルが表示されます。
6. **ICC プロファイルを保存** をクリックします。編集後のバイト列が `<original>-edited.icc` としてダウンロードされます。

2 つのエディターは独立しています。XML を編集してから JSON を編集しても、2 つの経路が混ざることはありません。保存されるのは、最後に生成された ICC バイト列です。

<div class="note">
<strong>注意：</strong>変換の忠実度は、IccLibXML / JSON ラッパーが各タグ型をどこまでサポートしているかに依存します。表現できないタグ型があると、ラウンドトリップで情報が失われます。書き戻した後に検証タブを確認し、すべて問題なく解析されることを確かめてください。
</div>

タグタブでは、読み込み時からバイト列が変わったタグがハイライトされるので、編集で何が変わったかを簡単に確認できます。

## 6. chardata からの起動 {#6-launching-from-chardata src=b39a6805}

**chardata** で ICC プロファイルを読み込んだ後、**Display File** をクリックしてページ内ビューアーを開き、**Launch editor** をクリックします。URL に `?source=chardata` が付いた新しいタブで、このツールが開きます。

受け渡しはすべてブラウザ内で行われます：

1. profiletool が開き、`?source=chardata` を検出して、`postMessage` で `window.opener` に `{type:'profiletool:ready'}` を送ります。
2. chardata が `{type:'profiletool:load', filename, bytes}` で応答します。
3. profiletool は（送信元のオリジンを許可リストと照合し、サイズを 256 MB の上限と照合した後で）バイト列を受け取り、検証を実行してプロファイルを表示します。

アップロードもサーバーとの往復もありません。流れは一方向です。ここで行った編集は **ICC プロファイルを保存** をクリックして保存するもので、chardata に返されることはありません。

## 7. URL での起動 {#7-launching-with-a-url src=f9a8d871}

**URL フラグメント**（`#` の後ろの部分）を使うと、読み込むプロファイルと最初に表示するタブを指定したリンクでツールを開けます：

```
https://chardata.colourbill.com/profiletool#url=<profile-url>&tab=<tab>
```

どちらのパラメーターも省略可能です：

- **`url=`** — プロファイルを取得する Web アドレス。バイト列はブラウザ内でダウンロードされ、ローカルファイルとまったく同じ経路で処理されます：`acsp` ヘッダーのチェック、完全な `ValidateIccProfile`、256 MB のサイズ上限、解析できないプロファイルに対するベストエフォートのフォールバック。何もアップロードされません。取得したバイト列はバリデーターに渡されるだけで、再送信されることはありません。
- **`tab=`** — プロファイルの読み込み後に開くビュー。

完全な例：

```
https://chardata.colourbill.com/profiletool#url=https://example.org/profiles/sRGB.icc&tab=VAL
```

<div class="note">
<strong>なぜクエリ文字列ではなくフラグメントなのか？</strong> <code>#</code> 以降の部分は Web サーバーに送信されないため、検査しているプロファイルのアドレスはお使いのマシンの外に出ません。
</div>

### タブ名 {#tab-names src=d3a4dbae}

`tab=` には、大文字と小文字を区別しない、互いに置き換え可能な 2 つの命名方式を使えます。推奨は**短い**コードです：

| ビュー | 短いコード | 長い名前 |
|---|---|---|
| ヘッダー | `HEADER` | `Header` |
| タグ | `TAGS` | `Tags` |
| 検証 | `VAL` | `Validation` |
| 分析 | `ANALYSIS` | `Analysis` |
| XML | `XML` | `XML` |
| JSON | `JSON` | `JSON` |

長い名前は、英語の画面上のタブラベルからスペースを除いたものです。表示ラベルが変更されてもどちらの方式も変わらないため、既存のリンクは引き続き機能します。検証タブは従来のコード `PAWG` にも対応しています（以前は「Profile Assessment WG」というラベルでした）。認識できない `tab=` の値は無視され、ヘッダービューが開きます。

<div class="note">
<strong><code>url=</code> の要件：</strong>プロファイルは <strong>HTTPS</strong> で配信されている必要があり、配信元のサーバーがクロスオリジンの読み取りを許可している（許可する <code>Access-Control-Allow-Origin</code> / CORS ヘッダーがある）必要があります。どちらかが欠けているとブラウザがダウンロードをブロックし、ツールは取得エラーを表示します。プロファイルの URL 自体に <code>&</code> や <code>#</code>（独自のクエリ文字列）が含まれる場合は、それらの文字でフラグメントが途中で終わらないよう、<code>url=</code> の値全体をパーセントエンコードしてください。
</div>

## 8. モバイル {#8-mobile src=cb948e3c}

幅 700 px 未満の画面では：

- 設定パネルは、右からスライドインするドロワーに収納されます。
- 右上の **⚙** フローティングボタンで設定を開閉します。
- ⚙ の下の **?** ボタンで、このガイドがスライドインペインで開きます。
- **✉** ボタンで、お問い合わせフォームが新しいブラウザタブで開きます。
- 暗くなった背景をタップすると、開いているドロワーが閉じます。
- タグの表は横長のグリッドから縦に積み重ねたカードに再配置されるので、横スクロールなしですべての列を読めます。タグはこれまでどおりその場で展開できます。
- **ドラッグ＆ドロップの代わりにタップを使います。** iOS にはドラッグ＆ドロップがないため、プールからタブへプロファイルをドラッグすることはできません。代わりに**プロファイルをタップして選択し、送りたいタブをタップ**してください。ドラッグと同じ結果になります。タッチスクリーンの使用中は、プールにこの案内が表示されます。
- **iPhone と iPad では、ファイル選択画面にすべてのファイルが表示されます。** iOS はファイルの種類によるフィルターを既知の種類とだけ照合しますが、`.icc`、`.icm`、`.cube`、`.exr` の種類を認識しないため、フィルターをかけると開きたいファイルそのものがグレーアウトされてしまいます。プロファイルは名前で選んでください。プロファイルでないものは、読み込み後に理由を示して拒否されます。

すべての機能が利用でき、レイアウトは小さな画面に合わせて調整されます。

## 9. 制限とセキュリティ {#9-limits-and-security src=ce1e9474}

profiletool は、最初のページ読み込みの後はネットワークリクエストを行いません。バリデーター、XML コンバーター、JSON コンバーター、画像コーデックはすべて C++ ソースからコンパイルされた WebAssembly で、完全にクライアント側で動作します。HDR タブはドロップされた画像をローカルのオブジェクト URL を通して表示するため、画像がタブの外に出ることはありません。**ディスプレイを識別**がウィンドウのあるモニターを問い合わせる相手は、サーバーではなくブラウザです。

| 制限 | 対象 | 備考 |
|---|---|---|
| **256 MB** | postMessage / ファイル読み込み | これより大きいものは読み込みを拒否し、悪意のある opener によるヒープ枯渇を防ぎます |
| **32 MB** | XML および JSON コンバーター | JS 側のガード（`MAX_XML_BYTES` / `MAX_JSON_BYTES`）と C++ ラッパー（`kMaxXmlBytes` / `kMaxJsonBytes`）の両方がこの上限を適用します。C++ 側は JS 側に依存せず単独で上限を保証します |
| **XML エンティティ爆弾ガード** | XML コンバーター | `<!DOCTYPE` や `<!ENTITY`、または NUL バイトを含む XML は、libxml2 に渡る前に拒否されます。libxml2 自身のエンティティ展開制限も有効なので、これは billion laughs 型の入力に対する第二の防御層です |
| **512 MB** | HDR タブのファイル | ファイルを読み始める前に、そのサイズで確認します。画像コーデック自身の 512 MB の入力上限と同じ値です |
| **40 メガピクセル**、**1 バイトあたり 64 ピクセル** | Radiance HDR のデコード（HDR タブ） | どちらもピクセル用のメモリを確保する前に、ヘッダーとファイルサイズから確認します。後者は反復マーカーによる展開爆弾を拒否します |
| **EXR デコード予算** | OpenEXR のデコード | 幅 × 高さ × チャンネル数 × 4 バイトが 512 MB に収まる必要があり、デコーダーが何かを確保する前にヘッダーから確認します |
| **HEIC/AVIF ボックス走査** | プロファイル抽出 | ボックスサイズはオーバーフローを起こさない方法で確認され、入れ子は 8 段、プロファイルは 64 MB（ファイルごとの合計）、アイテムの関連付けは 65 536 件が上限です |
| **オリジン許可リスト** | postMessage による起動 | `profiletool:load` のバイト列を送信できるのは、同一オリジンと chardata の開発ホストのオリジンだけです |
| **HTTPS + CORS** | `#url=` による起動 | URL 起動のプロファイルは、クロスオリジンの読み取りを許可するホストから HTTPS で配信されている必要があります。取得したバイト列はバリデーターにだけ渡され、再送信されることはありません |

`#url=` による起動（1.1.5 で追加）は、ページ読み込み後にツールが別オリジンへのリクエストを行う唯一のケースです。指定されたプロファイルを取得できるよう、Content-Security-Policy の `connect-src` を `https:` に広げています。スクリプトの読み込み元は広げて**いません**。広げているのはデータの取得だけです。

これらの制限を超えるプロファイルを検査する必要がある場合は、iccDEV をソースからビルドしてネイティブの CLI ツールを使ってください。それらには JS 側の上限はありません。

### ICC.2 (iccMAX) の対応範囲 {#icc-2-iccmax-coverage src=3d2b33e8}

**ICC.1** と **ICC.2** の両方のプロファイルに対応していますが、ICC.2 への対応は**不完全**です。読み込み、ヘッダーとタグのビュー、検証、XML/JSON のラウンドトリップ、変換エンジンはいずれも ICC.2 を理解します。既知の不足は、マルチパートの **ICS** 交換ワークフロー、変換適用時の V5 **サブプロファイル**の選択、一部の ICC.2 プロファイルでの逆探索です。サポートされていない ICC.2 の構造を使うプロファイルは、誤って読み取られることなく、検証タブで報告されます。
