ICC プロファイルツール — ヘルプ

ICC.1 および ICC.2 (iccMAX) プロファイルのためのブラウザベースの検査・検証・ラウンドトリップ編集ツール

ICC プロファイルツール（ICC Profile Tool、profiletool）は、ICC.1 および ICC.2 (iccMAX) カラープロファイルの検査、検証、ラウンドトリップ編集を行うブラウザベースのツールです。ICC 公式の IccProfLib デモ実装である iccDEV の WebAssembly ビルドを使い、すべてブラウザ内で動作します。アップロードもインストールも不要です。

できること：

  • ヘッダーの閲覧 — 128 バイトのプロファイルヘッダーの全フィールドを、人が読める文字列にデコードして表示します。
  • タグディレクトリの閲覧 — すべてのタグについて、シグネチャ、型、バイトオフセット、サイズ、パディングバイトを表示します。タグをクリックすると型ごとの詳細な説明（iccDEV の wxProfileDump の「Describe」ビューと同じ出力）が展開され、対応するタグではインラインの可視化も表示されます。トーンレスポンスカーブ、色度図、CLUT 画像と色域画像、名前付きカラーの散布図、さらに単一点の変換評価機能です。
  • 検証 — ICC Profile Assessment Working Group のチェックリスト（セキュリティ / 適合性 / 品質）を実行します。各チェックには判定が付き、カテゴリーで絞り込めます。
  • ラウンドトリップ編集 — プロファイルを XML または JSON に変換し、内蔵のコードエディターで編集して ICC に戻し、再検証します。保存ボタンで編集後のバイナリをダウンロードできます。
  • プロファイルのチェーン — リンク タブで、プール内のプロファイルを順序付きのチェーンにドラッグし、それを DeviceLink に焼き込む、チェーンを通して画像を変換する（出力のエンコーディング、圧縮、プレーナー配置、ICC 埋め込みを細かく指定可能）、またはカラーデータセットを変換することができます。
  • HDR の扱い — プロファイルを ICC.1 の HDR ColorSpace Profile の規則（箇条 8.7.1）に照らしてチェックし、cICP のコードポイントを読み取り、任意のディスプレイヘッドルームでのアダプティブゲインカーブをプロットします。HDR タブでは HDR 画像を 1 枚ディスプレイに表示でき、設定 → 環境 ではこのブラウザとディスプレイで何ができるかを確認できます。
  • chardata から起動 — chardata で読み込んだプロファイルを、そのままここで開きます。バイト列はブラウザ内で postMessage により受け渡されます。
  • URL で起動 — Web 上のプロファイルをツールに指定するリンクを開きます。必要に応じて最初に表示するタブも指定できます（例：…/profiletool#url=…&tab=VAL）。

すべてクライアント側で動作します。プロファイルのバイト列がブラウザのタブの外に出ることはありません。

ICC.2 (iccMAX) のサポートは部分的です。 ICC.2 プロファイルも ICC.1 と同様に読み込み、検査、検証、ラウンドトリップができます。検証チェックリストには iccMAX 固有のチェックが含まれ、スペクトル PCS やマルチプロセッシングエレメントのタグはデコードされ、変換エンジンは iccMAX の全機能を対象にビルドされています。未対応なのは、マルチパートの ICS（Interchange Color Space）ワークフロー、変換適用時の V5 サブプロファイルの選択、一部の ICC.2 プロファイルでの逆探索です。より特殊な ICC.2 機能には未対応の部分があると考えてください。リリースごとに順次対応しています。
HDR ColorSpace Profile のサポートはドラフトに準拠しています。 HDR チェック、headroomAdaptiveGainCurveTag のビュー、HDR タブは、現時点での ICC.1 HDR 改訂版を実装したものです。この改訂版はまだ発行されていないため、発行までに詳細が変わる可能性があります。

1. ワークスペース

profiletool は複数のプロファイルを扱うワークベンチです。ウィンドウは 3 つの部分で構成されます。

  • 左側のプロファイルペイン — 読み込んだすべてのものを入れておくプールです。
  • 右側のキャンバス — 上部に プロファイル、比較、リンク、スペクトル、HDR の 5 つのタブがあります。
  • 右端の設定ブレード（設定パネルを参照）。

プロファイルの読み込み

ファイルは次のどちらかの方法で読み込みます。

  • プロファイルペインの上部にあるプロファイルを読み込むをクリックし、1 つ以上のファイルを選択する。
  • ファイルをプロファイルペインにドラッグ＆ドロップする。

.icc / .icm プロファイルだけでなく画像も読み込めます。TIFF、PNG、JPEG、HEIC、AVIF をドロップすると、ツールはその埋め込み ICC プロファイルを抽出してプールに追加します。読み取るのはファイルのメタデータだけで、ピクセルは読みません。HEIC と AVIF ではファイルのボックス構造をたどるため、これらの形式を表示できないブラウザを含め、どのブラウザでも動作します。JPEG XL ファイルは受け付けません。プロファイルがコードストリーム内で圧縮されており、profiletool はまだその展開に対応していないためです。HEIC と同じコンテナを使う動画やカメラ RAW ファイル（MP4、QuickTime、Canon CR3）は画像として扱われません。OpenEXR と Radiance HDR（.hdr）ファイルは理由を示して拒否されます。どちらの形式にも ICC プロファイルを格納する場所がないためです。OpenEXR は色度座標で、Radiance HDR は任意の PRIMARIES ヘッダー行で色を表します。画像を表示するには HDR タブを使います。＋ .cube から新規作成ボタンでは、.cube LUT から DeviceLink を作成できます。結果はプールに追加され、プロファイルタブで開かれます。ICC プロファイルを保存をクリックするまで何もダウンロードされません。

プロファイルとして受け付けられるのは、先頭 36 バイトに acsp シグネチャを含み、IccProfLib の ValidateIccProfile で解析できるファイルです。受け付けられなかったファイルは具体的な理由とともに拒否の一覧に表示され、そのバイト列は保持されません。

プロファイルペイン

読み込んだプロファイルは、プロファイルクラス（Input、Display、Output、DeviceLink、ColorSpace、Abstract、Named Color など）ごとに、折りたたみ可能なセクションにまとめられます。ただし ICC.1 箇条 8.7.1 の HDR ColorSpace プロファイルは、一番上の専用セクションに表示されます（ColorSpace クラスのプロファイルなので、ColorSpace セクションから取り出して表示されます）。このセクションは伝達関数によってリニア伝達関数と非リニア伝達関数（PQ、HLG）に分かれ、各行には伝達関数がバッジで表示されます。この区別は HDR タブで意味を持ちます。OpenEXR や Radiance HDR の画像に割り当てられるのは、リニア伝達関数のプロファイルだけだからです。各行にはファイル名と、クラス、色空間、バージョン、サイズのバッジが表示され、一部しか解析できなかったプロファイルにはフラグが付きます。A–Z ボタンで並べ替え順を切り替え（読み込み順 → 昇順 → 降順）、行の × で削除し、ペイン右端のハンドルで幅を変更できます。ペイン全体を折りたたむこともできます。

行をクリックすると選択され、Ctrl/Cmd+クリックで選択の切り替え、Shift+クリックで範囲選択ができます。行をプールからタブへドラッグすると、そのタブで使えるようになります。

プールはそのセッション限りです。 何もアップロードされず、何も保存されません。永続的な保存先はあくまでお使いのファイルシステムです。ページを再読み込みするとプールは空になります。

スペクトルタブと HDR タブは、プール内のプロファイルではなく画像ファイルを直接受け取ります。その他の各タブはそれぞれ独自のプロファイルの組を持ち、それらはタブストリップの下に削除可能なチップとして表示され、タブ自体には件数のバッジが付きます。最初に読み込んだプロファイルは自動的にプロファイルタブで開かれます。それ以降は、プールから目的のタブへドラッグしてください。ファイルを直接タブにドロップすると、プールへの読み込みとそのタブへの配置が一度に行われます。

サイズ上限：256 MB を超えるファイルは読み込まれません。実際のプロファイルは通常 10 MB を大きく下回ります。この上限は、悪意のあるドロップや postMessage によってタブの WASM ヒープが使い果たされるのを防ぐためだけのものです。

2. 設定パネル

画面右端の ⚙ ボタン（モバイルでは右上の歯車アイコン）をクリックすると設定が開きます。パネルはコンテンツの大きさを変えずに、その上にスライドして表示されます。

⚙ の下には、さらに 2 つのボタンがあります。

  • ? はこのガイドをアプリ内で、ウィンドウの上にスライドインするペインとして開きます。ヘッダーには検索ボックスがあり、入力すると一致箇所がハイライトされます。Enter / Shift+Enter（または ˄ ˅ ボタン）で一致箇所を順に移動でき、Escape で検索をクリア、もう一度 Escape を押すとペインが閉じます。
  • ✉ は colourbill.com のお問い合わせフォームを新しいブラウザタブで開きます。

パネルには表示と環境の 2 つのグループがあります。パネルの幅は左端をドラッグして変更でき（220–560 px）、その幅は記憶されます。

背景

アプリのテーマをライト、ダーク、システム（OS の設定に従う）から選びます。選択はセッションをまたいで保持されます。システムモードでは、アプリが prefers-color-scheme を監視し、OS のテーマが変わると自動的に切り替わります。ライトまたはダークを明示的に選ぶと、この監視は解除されます。

数値形式

プロファイルビュー全体での数値の表示方法を、16 進数または 10 進数から選びます。

言語

インターフェースの言語を指定します。システム既定 (…) はブラウザのロケールを検出し、対応言語のうち最も近いものを使います。括弧内にはその言語の自言語名が表示されるので、どの言語が選ばれたかがわかります。翻訳の対象はアプリの UI 部分です：プロファイルペイン、タブのラベル、リンク・スペクトル・HDR の各ツール、タグ内の HDR ゲインカーブのビュー、環境とその理由表示を含む設定パネル、このガイドの UI 部分。翻訳されないテキストもあります。

  • IccProfLib が生成する文字列（タグの説明、検証メッセージ、ヘッダーのフィールド名）は、C++ ライブラリから英語のまま出力されます。
  • ブラウザフラグの名前は、ブラウザ自身のフラグページと一致するよう英語のままです。
  • 環境パネルのディスプレイイベント（Display events）のログは、そのままバグ報告に貼り付けられるよう英語のままです。
  • このガイドも同じ設定に従いますが、HDR のセクションは例外です。HDR サポートはベータ版で本文がまだ変わり続けているため、英語のままです。また、翻訳の最終更新以降に英語版が改訂されたセクションも、翻訳が追いつくまで注記付きで英語で表示されます。

対応言語：English、Français、Deutsch、Italiano、Español、Português (PT)、Português (BR)、Svenska、中文（简体）、中文（繁體）、日本語、한국어。chardata の設定パネルも同じ言語に対応しているため、一方のアプリで言語を切り替えると、もう一方でも一貫した表示になります。

環境

このブラウザ、プラットフォーム、ディスプレイで何ができるかを表示します。形式や HDR 機能が使えないときに、その理由を確認できます。上から順に：

  • 概要 — ブラウザとオペレーティングシステム、およびディスプレイが HDR を報告しているかどうか。
  • ブラウザのフラグ（Chrome、Edge、Opera、Brave）— Experimental Web Platform features が有効かどうか。このフラグは HDR キャンバスを有効にし、ページがディスプレイの HDR ヘッドルームを読み取れるようにします。

    • - フラグが無効だと判明している場合は、ボックスがハイライトされます。このブラウザで使用できる WebGPU がない場合は、HDR キャンバスが HDR を描画する唯一の手段となるため必須と表示されます。それ以外の場合は任意です。 - プロファイルの検査には一切必要ありません。 - Web ページからブラウザのフラグを開いたり変更したりすることはできません。コピーをクリックし、そのアドレスをアドレスバーに貼り付け、フラグを Enabled に設定してから、ブラウザを再起動してください。

  • ディスプレイ情報 — HDR ディスプレイ、広色域（sRGB、Display P3、Rec. 2020）、ピクセル比、および使用中の HDR キャンバス経路（float16-canvas、webgpu、またはなし）。条件の異なる画面へウィンドウをドラッグすると、これらは自動的に更新されます。切り替わるのは、ウィンドウの大部分が新しい画面に移ったときです。
  • ディスプレイを識別（Chromium 系ブラウザ）— ウィンドウがどのモニター上にあるかを確認する許可を求めます。許可すると、見た目の似たモニター間でもパネルが更新され、現在のモニターの名前と、ブラウザが公開している場合（上記のフラグを有効にした Chrome）は HDR ヘッドルームが表示されます。例：1.35 段（≈ SDR 白の 2.55 倍）。許可を拒否した場合は、サイトの設定で変更してください。
    • - ヘッドルームは SDR 白より上の余裕なので、ノートパソコン内蔵の HDR パネルでは輝度を上げると小さくなり（SDR 白が明るくなる一方、パネルのピークは変わらないため）、輝度を下げると大きくなります。HDR を見るときは輝度を下げてください。 - Windows では、輝度を変更してから数秒後、ディスプレイドライバーが値を報告した時点で新しい値が反映されます。ウィンドウが別の画面に移動したときや、Chrome が再びアクティブなアプリになったときにも更新されます。
  • ディスプレイイベント — 直近 20 回の更新と、それぞれのきっかけを記録した折りたたみ式のログです。ディスプレイの問題を報告するときに役立ちます。
  • 形式の表 — 形式ごとに 1 行（ICC プロファイル、TIFF、PNG、JPEG、OpenEXR、Radiance HDR、AVIF、HEIC/HEIF、JPEG XL）で、次の 3 つの問いに答えます：
    • - 検査：埋め込みプロファイルを読み取れるか。 - 表示：ピクセルを表示できるか。 - HDR：白より明るく描画できるか。

✕ の理由は、行にポインターを重ねると表示されます。表示できない形式は、表の下に理由とともに一覧表示されます。ドットの付いた形式は profiletool 自身がデコードするもので、どのブラウザでも同じように動作します。検査は、プロファイルがコードストリーム内で圧縮されている JPEG XL を除き、すべての形式で ✓ です。

3. プロファイルビュー

プロファイルを検査するには、プールからプロファイルタブへドラッグします。タブの上部には、ファイル名と ICC プロファイルを保存 ボタン（編集後は ● 変更あり — 未保存 のピルも）を表示するバーがあり、その下にビューアーがあります。ビューアーにはタイトルバー（ファイル名 · バイト単位のサイズ · IccProfLib のバージョン · 有効性バッジ）と独自のタブストリップがあります。

バッジは検証レポートの要約です：失敗や警告のチェックが 1 つもなければ緑の合格、警告のチェックが 1 つ以上あれば黄色の警告、失敗したチェックが 1 つでもあれば赤の不合格です。

一部しか解析できなかったプロファイル：プロファイルの損傷が大きく、バリデーターが構造しか読み取れない場合は警告バナーが表示され、ヘッダーとタグのタブだけが使えます。検証、分析、XML、JSON は非表示になります。そのプロファイルを適用してはならないためです。

3.1 ヘッダー

ICC プロファイルの 128 バイトのバイナリヘッダーの全フィールドを 2 列の表で表示します。値は IccProfLib の CIccInfo を使って人が読める文字列にデコードされます（シグネチャの展開、日付の整形、固定小数点値の変換）。プロファイル ID（ヘッダー内の MD5 ハッシュ）は、上部のハイライトされた帯に表示されます。

3.2 タグ

プロファイルのタグディレクトリにあるすべてのタグを 6 列のグリッドで表示します。

列意味
#ディレクトリ内の位置（1 から始まる）
Name人が読める長い名前（例：profileDescriptionTag）
ID4 文字のシグネチャ（例：desc）
Offsetファイル先頭からのバイトオフセット
Sizeタグデータのバイトサイズ
Padこのタグと次のタグの間のパディングバイト

タグの型シグネチャ（例：descType、mft2、mAB）は、展開したタグの上部にオフセットとサイズとともに表示されます。

タグはオフセット順に並びます。パディング列は色分けされ、Pad < 0（タグの重なり、規格非準拠）は赤、Pad > 3（仕様を超えるパディング）は黄色で表示されます。

行をクリックすると、その場で展開されます（アコーディオン形式で、一度に開けるタグは 1 つ）。展開した詳細の最後には、必ず型ごとの完全な説明が表示されます。これは IccProfLib の CIccTag::Describe(verbosity = 100) を実行した結果と同じです。大きな CLUT やカーブを含むタグ（例：A2B0、B2A0）では、すべてのグリッドセルやカーブ点が含まれます。

その説明の上には、可視化できるデータを持つタグについて、1 つ以上のインライン可視化が、それぞれ折りたたみ可能なセクションとして表示されます。

タグの種類可視化
トーンカーブ（rTRC/gTRC/bTRC/kTRC）トーンレスポンスカーブを恒等直線とともにプロットします。カーブ表はその下に折りたたまれています。
RGB 色材（rXYZ/gXYZ/bXYZ）と白色点（wtpt）該当する原色（または白色点）をハイライトした CIE 1931 色度図。色材 / 白色点のデータはその下に表示されます。
LUT 変換（A2B0–3、B2A0–3、gamt、pre0–2）入力側と出力側のトーンカーブ（重ねて表示し、色材ごとに色分け。凡例で各トレースの表示を切り替え可能）、画像化した CLUT 格子、色域画像（プロファイルの gamutTag 用。ニュートラル = 色域内、赤 = 色域外で色分け）、評価機能（後述）、折りたたまれた生データの表。
名前付きカラー / 色材テーブル（ncl2/nmcl/clrt/clot）CIELAB a*b* 図（および CIE xy 図）上の色の散布図。テーブルはその下に折りたたまれています。
符号化非依存コードポイント（cicp）コードポイント：色の原色、伝達特性、マトリクス係数、フルレンジフラグを、それぞれ ITU-T H.273 の定義どおりの名前で表示します。H.273 で割り当てられていない値や、ゼロでない予約バイトにはフラグが付きます。
アダプティブゲインカーブ（headroomAdaptiveGainCurveTag）指定ディスプレイヘッドルームでのゲインと、タグが代替画像を保持している場合はゲインカーブ。後述の HDR gain curves (HAGC) を参照してください。
不正なデータも隠しません。 カーブなどの可視化要素が IccProfLib の検証に通らない場合（例：ガンマが 0 に縮退したトーンカーブ）でも、グラフを黙って省略するのではなく、描画できる部分を描画し、ライブラリが示す正確な理由とともに ⚠ 警告を表示します。

変換の評価機能

LUT 変換（A2B / B2A / プレビュータグ）では、評価セクションで、そのタグの変換を指定した単一の色に適用できます。外部のカラーエンジンは使わず、IccProfLib を直接使います。方向はタグに従い（A2B はデバイス → PCS、B2A は PCS → デバイス）、レンダリングインテントもタグで決まります（…0 は知覚的、…1 は相対比色、…2 は彩度）。

  • 入力は浮動小数点値（デバイスチャンネル、または人が読める Lab/XYZ 単位の PCS）で指定するか、タグに CLUT がある場合はグリッド点のインデックス（格子上のノード位置）で指定します。
  • 出力は、内部の正規化された 0–1 エンコーディングと、人が読める単位（PCS の結果なら Lab/XYZ）の両方で表示されます。

色域タグ（gamt）には評価機能はありません。可逆な変換ではなく、1 チャンネルの色域内 / 色域外マップだからです。代わりに色域画像が表示されます。

HDR gain curves (HAGC)

This section is in English only. It describes HDR support, a beta feature that follows a draft ICC amendment and is still changing. It will be translated once the feature and its text are stable.

A headroomAdaptiveGainCurveTag says how an HDR ColorSpace Profile's image should be tone-mapped for displays with different amounts of headroom. Expanding the tag shows two views:

  • Gain curve plots the control points exactly as stored in the file, one line per alternate image. It is absent when the tag stores no alternate images. The x axis is the curve input: linear light, with 1.0 at the tag's HDR reference white. The y axis is the gain in stops, which is negative for an alternate that tones down.
  • Gain at a display headroom shows the curve as a colour-managed transform applies it, computed by IccProfLib's own evaluator. Drag Display headroom from 0 to 6 stops; it starts at the tag's baseline, and Baseline returns there. Two plots follow the slider:

    • - Gain applied at this headroom: the blended curve, drawn against every curve in the tag; - Grey tone curve at this headroom: what a grey input becomes, drawn against no change and the display peak.

Three more views make the adaptation visible: - Preview through the colour engine runs one test strip through IccProfLib's HDR transform twice: a grey ramp, then pure R, G, B, Y, C and M bands, all rising left to right in the profile's own signal (PQ, HLG, or Linear on a log scale). The top strip is as authored, at the baseline headroom where the tag applies no gain. The bottom strip is tone-mapped for the slider's headroom. Both are capped at that headroom's peak, the way a display with that much headroom would show them. Where the top strip clips to flat, the gain curve rolls the highlights off. Ticks mark where the ramp reaches reference white and the display peak. The strips use the same HDR output as the HDR tab: on an HDR display, values above SDR white look brighter than it. - Gain across every headroom is a heatmap of the gain on a grey input. The horizontal axis is input brightness, in stops relative to HDR reference white; the vertical axis is display headroom from 0 to 6 stops. Blue compresses, red expands, white leaves the input unchanged. Dotted lines mark the curves stored in the tag, the solid line the baseline, the amber line the slider, and the dashed diagonal where the input reaches the display peak. Click the heatmap to move the slider to that headroom. - Grey tone curves by headroom overlays the tone curve at each headroom the tag stores, shaded from blue (low) to red (high), with the slider's curve in amber. Both axes are in stops, so the diagonal means no change.

A note appears when slopes or whole curves are derived rather than stored. Another appears when the headroom is outside the tag's range, in which case the nearest curve is used unchanged.

Two cases have no curves to draw, and the view still explains them: - Tone mapping on, no alternate images. The tag asks for no tone mapping, only a clamp to what the display can show. The gain is zero at every headroom, and the preview strip shows the clamp. - Tone mapping off (the tag's Headroom Adaptive Tone Map flag is clear), or a tag IccProfLib cannot apply. The view says why IccProfLib declines, and a colour engine falls back to the next tone-mapping method (clause 8.7.1.3).

3.3 検証

読み込んだプロファイルに対して ICC Profile Assessment Working Group のチェックリストを実行し、レポートとして表示します。チェックは iccDEV の iccPawgReport ツールに由来し、別の WebAssembly モジュールとしてコンパイルされていて、このタブを初めて開いたときにだけ取得されます。（同じレポートがタイトルバーの有効性バッジにも使われ、URL 起動では VAL または従来の PAWG で指定できます。）

各チェックはセキュリティ、適合性、品質のいずれかに分類され、それぞれ 1 つの判定を持ちます。HDR コンテンツを含むプロファイルには、4 つ目のグループ HDR が加わります。その最初のチェックは、プロファイルが ICC.1 に適合する HDR ColorSpace プロファイル（箇条 8.7.1）かどうかを報告し、残りのチェックはこの箇条が依拠する HDR メタデータを確認します。

判定意味
合格 (PASS)チェックに成功しました
警告 (WARN)確認が望ましい、致命的ではない懸念事項です
不合格 (FAIL)プロファイルがチェックを満たしていません
ギャップ (GAP)チェックを完全には評価できませんでした（例：未実装）
該当なし (N/A)このチェックはこのプロファイルに適用されません
未実行 (NOT RUN)チェックはスキップされました

上部の要約行には、各判定の件数が色付きのピルで表示されます。ピルをクリックすると下のレポートを絞り込めます。青いハローは現在表示中のカテゴリーを示し、件数がゼロのピルは無効になります。たとえば 合格 (PASS) と 該当なし (N/A) をオフにすると、警告と不合格だけに集中できます。

3.4 分析

プロファイルのカラー変換から導き出す、プロファイル全体の品質分析です。専用の WebAssembly モジュール（iccDEV の可視化エンジン）で計算され、このモジュールはこのタブを初めて開いたときにだけ取得されます。結果はアプリ独自のスタイルでプロットされます。

各分析は折りたたみ可能なセクションで、最初はすべて閉じています。これは意図的なものです。どのセクションもプロファイル全体に対する変換処理を 1 回分必要とするため、タブを切り替えた瞬間に 6 つの分析が一斉に走るのではなく、開くかどうかを明示的に選べるようにしています。結果はキャッシュされるので、セクションを開き直すと即座に表示されます。読み込んだプロファイルに該当しないセクションには、代わりに短い該当なしの注記が表示されます（たとえば matrix/TRC のディスプレイプロファイルには、分析対象となるデバイス↔PCS の CLUT がありません）。

プロファイル統計

1 つの選択したレンダリングインテントについて、プロファイル全体の指標を表示します。2 つのリストボックスと 1 つのチェックボックスで操作します。

  • レンダリングインテント — 知覚的 / 相対比色 / 彩度 / 絶対比色。
  • ラウンドトリップの種類 — 報告する精度指標（後述）。
  • MPE（カラー）タグを使用 — オフでは測色用のルックアップテーブルを、オンではマルチプロセッシングエレメント / カラータグを使います。色域内の概要には影響しないため、その場合は無効になります。

表には、色域体積（ΔE*ab³ 単位。デバイス → PCS の A2B 変換が囲む体積で、境界をボクセル化して内部のセルを数えて測定）と、選択したラウンドトリップの最小 / 平均 / 標準偏差 / P90 / 最大 ΔE*ab が並んで表示されます。その下には ΔE 分布のヒストグラム（相対度数の棒グラフと累積度数の折れ線）があり、さらに誤差が最大となる L, a, b と、PRMG の場合はプロファイルが Perceptual Reference Medium Gamut を示しているかどうかが表示されます。

4 種類のラウンドトリップ：

  • 色域内の概要 (RT0) — デバイス値のグリッドを PCS へ変換し、デバイスへ戻し、再び PCS へ変換して、2 回の PCS 値の間で ΔE*ab を測定します。高速な色域内の安定性チェックです。
  • 反転 + 色域 (RT1) — 各デバイス色の PCS 値と、Lab → デバイス → Lab のラウンドトリップを 1 回行った後の PCS 値との ΔE*ab。反転の精度と色域マッピングの両方を反映します。
  • 再現性 (RT2) — 1 回目と 2 回目のラウンドトリップの間の ΔE*ab。1 回目の色域クリッピングとは無関係に、ラウンドトリップを繰り返したときの安定性を示します。
  • PRMG 相互運用性 — Perceptual Reference Medium Gamut 内の PCS 色を 1 回ラウンドトリップさせます。その ΔE 分布が、プロファイル間の相互運用性を示します。

ヒストグラムの下にある明度別のラウンドトリップ ΔE は、要約値では答えられない問い、つまり反転がトーンスケールのどこでうまくいっていないのか、そして問題が色域のどこまで内側に及んでいるのかに答えます。

32 段階の明度をサンプリングします。各明度で色域境界上の 64 点を取り、それらを中性軸に向けてクロマの 80 %、50 %、20 % まで縮めた点でも繰り返します。合計 8,192 点をそれぞれ個別にプロットし、明度レベルの間は点線で区切ります。

帯ごとに読んでください。1 つの帯の中では、点が左の色域表面から右のニュートラルへ並ぶため、誤差は帯の中で下がっていくはずです。境界付近の色は最も反転が難しく、ニュートラル付近の色は最も容易です。ニュートラルまで誤差が高いままの帯は、その明度でプロファイルに問題があることを意味します。最も高いスパイクは、色域境界そのものの反転が最もうまくいっていない明度レベルを示します。

すべてのシードは構成上色域内にあるため、見えているのは到達できない色がクリップされた結果ではなく、B2A/A2B の本当の不一致です。このプロットは独自のサンプリング（意図的に色域境界寄りに重み付け）を使うため、その平均と最大は上の表より高くなり、表とは比較できません。レンダリングインテントの選択には従いますが、ラウンドトリップの種類には従いません。

指標に必要なデバイス↔PCS 変換を持たないプロファイルには該当なしの注記が表示されます。サンプリングするには広すぎるデバイス空間は、エラーではなくスキップとして報告されます。

極値の測色

プロファイルの再現範囲の両端、つまり印刷オペレーターが通常まず確認する数値です。

  • 白色点 — 色材ゼロ、つまり素地そのものの色。
  • 黒色点 — PCS の黒（L*=0、a*=b*=0）を選択した B2A テーブルに通して、プロファイルが黒として選ぶインキングを求め、そのインキングを A2B1 で読み戻して求めます。
  • どちらも相対と絶対の測色値で表示されます。絶対は素地そのものの色を示し（青みがかった白い紙なら L* 95、b* −4 のような値になります）、相対は完全な白を基準に参照し直した値です。2 つの列が同じでも正常です。メディアの白が光源と一致しているだけです。メディア白色点タグのないプロファイルでは、相対のみが表示されます。
  • 黒色点でのインキングと TAC — その黒における各チャンネルのインキ量と、その合計である総面積率（インキ制限の値）です。

B2A テーブルはそれぞれ独自に黒のインキングを選ぶため、黒色点はインテントによって実際に異なります。レンダリングインテントのセレクターがあるのはそのためです。

その下のベタとクロマ最大点は、各インキのコーナー（C、M、Y、R、G、B、K）について、色相 / クロマ / 明度のどこに到達するかと、素地からそこへ向かう途中で見つかった最もクロマの高い点を示します。これらの行は A2B1 を通して測定されるため、インテントのセレクターでは変わりません。素直なプロファイルでは 2 つの行が一致します。ベタより前にクロマ最大に達した場合は、その行にフラグが付きます。その点を過ぎると、インキを増やしてもクロマは上がらず、暗くなるだけだからです。

出力（プリンター）プロファイルのみ — この分析は、色材ゼロ = 素地であることを前提としています。色相ごとの表には、さらに CMYK または CMY のデバイス空間が必要です。n 色（nCLR）プロファイルはチャンネルを任意の順序で命名するため、どのチャンネルが「シアン」かを判別できません。その場合、表は推測せずにその旨を報告します。

中立軸インキング

中性軸（a*=b*=0）を白（L*=100）から黒（L*=0）まで、プロファイルの B2A（PCS → デバイス）テーブルを通してスイープし、その間にプロファイルが各デバイス色材をどれだけ置くかをプロットします。古典的な GCR / ニュートラルビルドのカーブです。デバイスチャンネルごとに 1 本のカーブを、色材ごとに色分けして表示します。

分版の上には、さらに 1 本のカーブが描かれます：

  • L* 出力（トーン） — トーンレスポンス、つまりプロファイルをラウンドトリップした後に中性軸が実際にどの明度に着地するかです。その形から 2 つのことが読み取れます。対角線より下にたわんでいれば、グレーは指定より暗く再現されます。さらに有用なのは、カーブがプロファイルが到達できる最も暗い明度で平坦になることです。この平坦部こそがメディアの黒色点であり、上の「極値の測色」セクションの値と一致するはずです。

出力（プリンター）プロファイルのみ。その他のプロファイルクラスでは注記が表示されます。

シャドウ部のインキ使用量

意図的に暗くした一定の明度で、a*b* 平面を横切る 4 本の直線経路（0°、45°、90°、135°）を選択した B2A テーブルに通し、得られた分版をそれぞれプロットします。

経路上のすべてのサンプルが同じ L* を持つため、色材に急な段差や反転があれば、それは色相とクロマの処理だけに起因します。これはシャドウ部の色域マッピングのアーティファクトの特徴であり、印刷では暗部のバンディングや急な色ずれとして現れる類のものです。経路は色域のはるか外側から色域を通り抜けて反対側の外まで伸びるので、プロファイルがどこでクランプし始めるかもわかります。

明度の平面は自動的に選ばれます。プロファイルのブルーのコーナーと、C、M、Y、R、G のうち最も暗いものとの中間です。知覚的テーブルと彩度テーブルでは、まず明度をメディアの黒色点から PCS の黒まで引き伸ばします（これらのテーブルはそこに黒があることを前提としているためです）。セクションには、補償後の平面と元の平面の両方が表示されます。

出力（プリンター）プロファイルのみで、上の色相ごとの表と同じ CMYK/CMY の制限があります（平面はインキのコーナーから導き出されるため）。

中性軸を通る一次色インキ経路

3 本の経路（シアン→レッド、マゼンタ→グリーン、イエロー→ブルー）は、それぞれ一方の原色コーナーから、両端点の中間の明度で中性軸を通って反対側のコーナーへ向かいます。各経路を選択した B2A テーブルに通し、分版としてプロットします。

これは「シャドウ部のインキ使用量」の色域内版です。あちらでは経路が意図的に色域外を通り、色域マッピングのアーティファクトをあぶり出しますが、こちらではすべてのサンプルが構成上色域内にあります。両端点はプロファイル自身の原色で、ピボットは中性軸上にあるからです。したがって、これらの経路上で色材に段差、折れ、反転があれば、それは色域クリッピングのせいではなく、CLUT の滑らかさの欠陥です。ニュートラルのピボットは各プロットの中点にあり、そこではバランスの取れたニュートラルビルドが見えるはずです。

知覚的テーブルと彩度テーブルでは、「シャドウ部のインキ使用量」とまったく同じように、明度がインテントに合わせて黒点補償されます。

出力（プリンター）プロファイルのみで、同じ CMYK/CMY の制限があります（コーナーは色相ごとの表と同じソースから得られるため）。

インキ使用量の統計

プロファイルが各色材をどれだけ置くかを、平均被覆率と全体に占める割合で示します。分版のインキ消費の特徴を表すものです。

表は中性軸全体で各色材を合計し、その平均被覆率と、置かれた全インキに対する割合を報告します。診断に役立つのは割合の列です。これはプロファイルのニュートラルビルドの指紋のようなもので（シアンの多いグレーバランスとブラックの多いグレーバランスでは値が異なります）、サンプル数にも依存しません。

2 つ目の表である色域上および色域内のすべての色にわたるインキ使用量は、保留中として表示されています。まだ実装されていない色域境界の構築が必要なためです。

出力（プリンター）プロファイルのみ。

CLUT 画像

デバイス↔PCS 変換のカラールックアップテーブルを画像としてタイル表示します。どのレンダリングインテントのテーブルを表示するかを選ぶセレクター（A2B0–A2B3、B2A0–B2A3、プレビューテーブル）があります。テーブルの構造的な破損をひと目で見つけるのに役立ちます。ズーム、パン、リセットはキャンバス上のコントロールで行います。

B2A（PCS → デバイス）テーブルを選ぶと、格子の下に色材ごとのインキ被覆率画像がグレースケールで表示されます。インキごとの分版で、暗いほどそのインキが多いことを示します。セクションは A2B テーブル（出力はインキではなく L*a*b*）を表示した状態で開くため、セクション上部のヒントでこれらの画像を案内しています。単純なカラープレビューができない n 色（nCLR）出力（5 色、6 色、7 色）では、メイン画像がプロファイルの順方向 A2B でカラーマネジメントされるため、単一チャンネルのグレーではなく実際の色で描画されます。

色域画像

色域タグの色域内 / 色域外マップです。PCS の色が再現可能な箇所はニュートラル、デバイスの色域外にある箇所は赤で表示されます。プロファイルに gamt タグがある場合にのみ表示されます。

3.5 XML

プロファイルを XML に変換し（iccDEV の iccToXml CLI と同じライターである IccLibXML を使用）、シンタックスハイライト付きの CodeMirror エディターで表示します。XML を編集して ICC に変換 をクリックすると、バイナリに戻せます。ビューアーが再検証し、プロファイルタブのバーにある ICC プロファイルを保存 ボタンで結果をダウンロードできます。

エディターのテキストが最後の変換出力と異なると未保存のインジケーターが表示されるので、編集が反映済みかどうかがひと目でわかります。変換に失敗した場合は、IccLibXML の解析エラーが問題のある行 / 列とともにエディターの上に表示されます。

3.6 JSON

XML タブと同じ考え方ですが、バリデーターのラッパー（json-wrapper.cpp）が生成するプロファイルの JSON 表現を使います。編集し、ICC に変換 をクリックして保存します。JSON 形式はよりコンパクトでスクリプトから扱いやすく、XML 形式は iccDEV の CLI ツールを使ったことがあれば馴染みがあるでしょう。

4. リンクタブ

profiletool は、読み込んだすべてのプロファイルを左側のプロファイルプールに保持します。上部には 5 つのタブ、プロファイル（前述の単一プロファイルビューアー）、比較、リンク、スペクトル、HDR があります。リンク タブでは、プロファイルをチェーンにつないで活用します。チェーンから DeviceLink を作成したり、チェーンを通して画像を変換したり、カラーデータセットを変換したりできます。

4.1 チェーンの構築

プールから 1 つ以上のプロファイルをリンクパイプラインのカードにドラッグすると、順番にチェーンへ追加されます。チェーンは縦方向のスタックで、ソースが上、シンクが下です。各プロファイルは変換 1 つを担い、ツールはそこに入る色空間と出る色空間（例：RGB → Lab）を表示し、段と段の間の線には接続空間がラベル表示されます。エンジンはチェーン全体をリアルタイムで検証し、端から端までの流れ（例：チェーン：RGB → CMYK）を報告するか、接続できない箇所を段ごとに説明します。

  • 段の並べ替えは、グリップ（⠿）をドラッグするか ▲ / ▼ ボタンで行います。× で削除します。
  • 方向の反転 — 先頭の変換の ⇅ ボタンでチェーンの方向が反転し、後続の段にも順に反映されます。
  • レンダリングインテント — レンダリングインテント（すべて） でチェーン全体に 1 つを選ぶか、各段のリストボックスで個別に上書きします。どちらのコントロールもポインターを重ねると、選択中のインテントの説明が表示されます。4 つの基本インテントに加えて、必要なテーブルを持つプロファイルでは no D2Bx/B2Dx と + BPC（黒点補償）のバリエーションも選べます。
チェーン内の HDR ColorSpace プロファイル。 ICC.1 の HDR ColorSpace Profile には TRC タグがありません（箇条 8.7 は ColorSpace プロファイルに TRC タグを定義していません）。そのため、これを通る変換には AToB0Tag が使われます。このテーブルは、HDR 処理を持たないソフトウェアのために箇条 8.7.1.5 が要求する HDR→SDR レンダリングです。チェーンに HDR ColorSpace Profile が含まれる場合は、カードにその旨が表示されます。作成される DeviceLink、画像、データは、プロファイルの HDR の振る舞いではなく、この SDR フォールバックを反映したものになります。

4.2 DeviceLinkを作成

チェーン全体を 1 つの DeviceLink プロファイルに焼き込みます（iccDEV の iccApplyToLink をブラウザに移植したもの）。名前を付けて DeviceLinkを作成 をクリックすると、結果は他のプロファイルと同様にプールとリンクのアキュムレーターに追加され、プロファイルタブで検査したり、別のチェーンで再利用したりできます。

4.3 画像を変換

画像スロットにラスター画像（TIFF、PNG、JPEG）を 1 つドロップし、画像を変換 をクリックすると、チェーンを通して変換されます（iccApplyProfiles をブラウザに移植したもの）。画像はまずヘッダーだけを調べて検証され、その色空間がチェーンの入力と一致している必要があります。結果はダウンロードされます。画像がプールに保存されることはありません。

有効な画像が読み込まれると 画像出力オプション パネルが表示され、iccApplyProfiles CLI に対応する出力側の設定が並びます：

  • エンコーディング — 元と同じ、8 ビット、16 ビット、浮動小数点（32ビット）。
  • 圧縮 — なし、LZW、ZIP（Deflate）。
  • プレーナー — コンポジット（チャンキー）またはセパレートのプレーン。
  • CMM補間 — 四面体または線形。
  • ICCを埋め込む — チェーンの最後の（出力空間の）プロファイルを出力にタグ付けします。

既定では RGB/グレーの出力は PNG のままです。TIFF 専用の設定（浮動小数点、LZW/ZIP、セパレートプレーン）を選ぶと、コンテナが TIFF に切り替わります。

埋め込みプロファイル：ドロップした画像に ICC プロファイルが埋め込まれている場合は、それを抽出するよう促すバナーが表示されます。ワンクリックで、プロファイルがプールに追加され、チェーンの先頭（ソース空間）に配置されます。

4.4 データを変換

データスロットにカラーデータセット（CGATS/IT8、CSV、CxF、JSON）をドロップし、データを変換 をクリックすると、すべてのパッチがチェーンを通して変換されます（iccApplyNamedCmm 相当）。ツールはデータセットに含まれるデータの種類（デバイス / Lab / XYZ / スペクトル）を読み取り、チェーンの入力に必要なものを渡します。スペクトル入力は、選択した観測者と光源を使い、iccDEV の標準の計算器で測色値に変換されます。重複パッチは除外できます（中央値または平均値）。結果は表で開かれ、CSV として保存できます。

4.5 観察者の変更

リンクタブには2 つのメーカーカードがあります。リンクパイプラインの上にある 観察者の変更 カードは、V5 RGB ディスプレイプロファイルと V5 観測者（PCC）プロファイルから、v4.3 の matrix/TRC ディスプレイプロファイルを作成します。両方をカードにドラッグすると、プロファイルクラスに応じて V5 RGB ディスプレイ と V5 オブザーバー (PCC) のスロットに自動的に振り分けられます。次に V4 ディスプレイプロファイルを作成 をクリックし、名前を付けて 作成 をクリックします。結果はプールとこのタブに追加されます。どちらにも当てはまらないプロファイルは、警告とともに無視されます。

4.6 比較タブとスペクトルタブ

比較 タブは、プール内の 2 つ以上のプロファイルの色域境界を重ねて表示し（3D シェルと 2D の明度スライス）、どこが違うかを確認できます。プロファイルが HDR ColorSpace Profile の場合は SDR フォールバックを表示中 という注記が表示され、各色域がプロファイルの HDR レンジではなく AToB0Tag の SDR レンダリングから構築されていることを説明します。HDR レンジは有界な PCS では描画できないためです。スペクトル タブは、単一チャンネルのスペクトル画像のセット（チャンネル順にドロップ）を 1 つのマルチチャンネル TIFF にまとめます（iccSpecSepToTiff）。

So is a file whose pixel data is too small for its size: at most 64 pixels per byte, four times what run-length encoding reaches on a flat scanline. Old-style repeat markers could otherwise describe a 40-megapixel image in about 75 KB.

SDR canvas (tone-mapped): always available. It cannot show brighter-than-white, so the slider is hidden.

On the slider, 0% is the SDR rendering and 100% is no limit. Values in between cap brightness smoothly at that many stops above SDR white (0 to 6 stops), shown beside the slider.

Matching the display. The panel tracks the monitor the window is on: drag it to another screen and the facts and notes update.

It comes from the headroom the browser reports; see Environment, where Identify displays grants the permission (the button also appears here). An SDR display reads 1× — SDR display. When the browser does not report a peak, the panel says so rather than guessing.
  • When an OpenEXR or Radiance HDR image asks for more than the display shows, a note says so — for example asks for 4.93×, this display shows up to 2.23×. Values above the display's peak then clip to flat white, which is why the SDR and HDR ends can look alike even on an HDR monitor.
  • Fit to display sets the limit to the display's peak, so highlights roll off into it instead of clipping. On an SDR display that means the SDR rendering. On Windows the reported peak can lag behind brightness changes; the value is shown so you can judge.
  • An SDR white patch — plain white — sits against the image's right edge, for comparison by eye. Drag it anywhere over the viewer (or focus it and use the arrow keys; Shift for bigger steps), and double-click it to put it back beside the image. The SDR white patch button above the image turns it on and off. Its position and on/off state are remembered. On an HDR display with real HDR output, highlights look brighter than the patch; at the SDR end the brightest pixels sit just below it, because the SDR rendering eases highlights in under white. If highlights never look brighter, the output is being clamped.

  • The SDR white patch is not zoomed: it stays the same size wherever the image moves, and a docked patch follows the image's right edge.

Assigning an HDR profile. For TIFF, PNG, JPEG, OpenEXR and Radiance HDR, Assign profile chooses a profile to interpret the image's pixel values:

  • the image's embedded profile;
  • any HDR ColorSpace Profile in the pool (load one in the Profiles pane first);
  • None, to go back to what the file itself signals.

A TIFF starts with its embedded profile selected, since without one its values mean nothing.

With a profile assigned, profiletool decodes the image itself and runs it through IccProfLib's HDR colour-management path, as the ICC.1 HDR amendment (clause 8.7.1) describes. The profile's transfer function (PQ, HLG or Linear) converts the code values to light, its gain curve tone-maps them, and its cicpTag primaries set the colour. 1.0 lands on the profile's HDR reference white, which is shown at the display's SDR white.

  • Target headroom (0 to 6 stops) is the display the image is being prepared for. The profile's gain curve is evaluated there, the same curve Gain at a display headroom plots in the Tags tab. Fit to display sets it to this display's peak.
  • Tone mapping chooses the method: Auto (the clause 8.7.1.3 recommended ranking), Gain curve only, the profile's Baked SDR fallback (AToB0Tag), or Off, which behaves like a colour engine that predates the amendment. The baked fallback is only as good as the table the profile carries. A table baked from the gain curve (for example by iccDEV's iccHdrFallback) gives a proper SDR rendering. A placeholder table of identity curves passes the raw PQ or HLG signal values through, and the image looks flat and too bright.
  • The panel reports what the colour engine actually did: which path (HDR with the gain curve applied, HDR without a curve, or the baked table), the transfer, and the HDR reference white. A profile without a gain curve still takes the HDR path, but tone-maps nothing, so the Dynamic range limit is what keeps its highlights within the display.
  • Pooled HDR ColorSpace Profiles appear in two groups, Linear transfer and PQ / HLG transfer, matching the Profiles pane. OpenEXR and Radiance HDR store linear light, so for those images only the Linear transfer group is offered. A note under the list says so, and how many PQ/HLG profiles are hidden. Assigning needs a 3-channel RGB image.
  • A profile whose cicpTag declares ColourPrimaries 2 (Unspecified) is listed with the note Unspecified primaries: no HDR path in this build. Clause 8.7.1.1 takes such a profile's primaries from a cicpType chromaticity extension (clause 10.3) whose format is not yet available to profiletool, so no policy can give it an HDR rendering. Every policy renders it through its AToB0Tag instead — Auto and Gain curve fall back to the same SDR rendering as Baked SDR fallback and Off — and Colour engine path says Baked AToB0 — not the HDR path. That fallback is a temporary measure in IccProfLib while the ICC settles how such a profile should be handled.
  • Linear values (OpenEXR, Radiance HDR and floating-point TIFF only) says what a file value of 1.0 means. The two conventions disagree. These files usually put SDR white at 1.0, but an ICC Linear transfer reads 1.0 as 1 cd/m² (ICC.1 clause 8.7.1.2 a) and then divides by the HDR reference white, so an unscaled image comes out a few hundred times too dark.

    • - File 1.0 = HDR reference white (the default) multiplies the pixels by the profile's HDR reference white first, so file 1.0 lands on it. The Input scale fact shows the factor, for example ×300. - File 1.0 = 1 cd/m² passes the values unscaled, as the clause reads them. Use it for files whose values really are in cd/m².

The choice is remembered.

Why some images look dim: browsers ignore HDR that is signalled only by an embedded ICC profile. A PNG or JPEG whose HDR lives in an ICC.1 clause 8.7.1 HDR ColorSpace Profile therefore looks flat here. The panel says so when that applies. Its profile is still fully inspectable.
Refusals name the reason. For example, HEIC display needs Safari: Chrome and Firefox decode HEIC on no platform. The image's profile can still be opened in the Profile tab.

Gain curves. An HDR ColorSpace Profile's adaptive gain curve is not shown here but in Profile → Tags. See HDR gain curves (HAGC) under Tags.

5. ラウンドトリップ編集

XML タブと JSON タブは、どちらもプロファイルを ICC バイナリに書き戻せます。典型的な手順は次のとおりです：

1. ICC プロファイルを読み込みます。 2. XML または JSON タブを開きます。XML に変換 / JSON に変換 をクリックしてエディターに内容を表示します。 3. ページ内のエディターで編集します。ツールバーの横に未保存のインジケーターが表示されます。 4. ICC に変換 をクリックします。ラッパーが新しいプロファイルを生成し、検証を再実行して、ヘッダー / タグ / 検証の各タブを更新します。 5. プロファイルタブのバーで、ファイル名の横に ● 変更あり — 未保存 のピルが表示されます。 6. ICC プロファイルを保存 をクリックします。編集後のバイト列が -edited.icc としてダウンロードされます。

2 つのエディターは独立しています。XML を編集してから JSON を編集しても、2 つの経路が混ざることはありません。保存されるのは、最後に生成された ICC バイト列です。

注意：変換の忠実度は、IccLibXML / JSON ラッパーが各タグ型をどこまでサポートしているかに依存します。表現できないタグ型があると、ラウンドトリップで情報が失われます。書き戻した後に検証タブを確認し、すべて問題なく解析されることを確かめてください。

タグタブでは、読み込み時からバイト列が変わったタグがハイライトされるので、編集で何が変わったかを簡単に確認できます。

6. chardata からの起動

chardata で ICC プロファイルを読み込んだ後、Display File をクリックしてページ内ビューアーを開き、Launch editor をクリックします。URL に ?source=chardata が付いた新しいタブで、このツールが開きます。

受け渡しはすべてブラウザ内で行われます：

1. profiletool が開き、?source=chardata を検出して、postMessage で window.opener に {type:'profiletool:ready'} を送ります。 2. chardata が {type:'profiletool:load', filename, bytes} で応答します。 3. profiletool は（送信元のオリジンを許可リストと照合し、サイズを 256 MB の上限と照合した後で）バイト列を受け取り、検証を実行してプロファイルを表示します。

アップロードもサーバーとの往復もありません。流れは一方向です。ここで行った編集は ICC プロファイルを保存 をクリックして保存するもので、chardata に返されることはありません。

7. URL での起動

URL フラグメント（# の後ろの部分）を使うと、読み込むプロファイルと最初に表示するタブを指定したリンクでツールを開けます：

https://chardata.colourbill.com/profiletool#url=<profile-url>&tab=<tab>

どちらのパラメーターも省略可能です：

  • url= — プロファイルを取得する Web アドレス。バイト列はブラウザ内でダウンロードされ、ローカルファイルとまったく同じ経路で処理されます：acsp ヘッダーのチェック、完全な ValidateIccProfile、256 MB のサイズ上限、解析できないプロファイルに対するベストエフォートのフォールバック。何もアップロードされません。取得したバイト列はバリデーターに渡されるだけで、再送信されることはありません。
  • tab= — プロファイルの読み込み後に開くビュー。

完全な例：

https://chardata.colourbill.com/profiletool#url=https://example.org/profiles/sRGB.icc&tab=VAL
なぜクエリ文字列ではなくフラグメントなのか？ # 以降の部分は Web サーバーに送信されないため、検査しているプロファイルのアドレスはお使いのマシンの外に出ません。

url= の要件：プロファイルは HTTPS で配信されている必要があり、配信元のサーバーがクロスオリジンの読み取りを許可している（許可する Access-Control-Allow-Origin / CORS ヘッダーがある）必要があります。どちらかが欠けているとブラウザがダウンロードをブロックし、ツールは取得エラーを表示します。プロファイルの URL 自体に & や #（独自のクエリ文字列）が含まれる場合は、それらの文字でフラグメントが途中で終わらないよう、url= の値全体をパーセントエンコードしてください。

8. モバイル

幅 700 px 未満の画面では：

  • 設定パネルは、右からスライドインするドロワーに収納されます。
  • 右上の ⚙ フローティングボタンで設定を開閉します。
  • ⚙ の下の ? ボタンで、このガイドがスライドインペインで開きます。
  • ✉ ボタンで、お問い合わせフォームが新しいブラウザタブで開きます。
  • 暗くなった背景をタップすると、開いているドロワーが閉じます。
  • タグの表は横長のグリッドから縦に積み重ねたカードに再配置されるので、横スクロールなしですべての列を読めます。タグはこれまでどおりその場で展開できます。
  • ドラッグ＆ドロップの代わりにタップを使います。 iOS にはドラッグ＆ドロップがないため、プールからタブへプロファイルをドラッグすることはできません。代わりにプロファイルをタップして選択し、送りたいタブをタップしてください。ドラッグと同じ結果になります。タッチスクリーンの使用中は、プールにこの案内が表示されます。
  • iPhone と iPad では、ファイル選択画面にすべてのファイルが表示されます。 iOS はファイルの種類によるフィルターを既知の種類とだけ照合しますが、.icc、.icm、.cube、.exr の種類を認識しないため、フィルターをかけると開きたいファイルそのものがグレーアウトされてしまいます。プロファイルは名前で選んでください。プロファイルでないものは、読み込み後に理由を示して拒否されます。

すべての機能が利用でき、レイアウトは小さな画面に合わせて調整されます。

9. 制限とセキュリティ

profiletool は、最初のページ読み込みの後はネットワークリクエストを行いません。バリデーター、XML コンバーター、JSON コンバーター、画像コーデックはすべて C++ ソースからコンパイルされた WebAssembly で、完全にクライアント側で動作します。HDR タブはドロップされた画像をローカルのオブジェクト URL を通して表示するため、画像がタブの外に出ることはありません。ディスプレイを識別がウィンドウのあるモニターを問い合わせる相手は、サーバーではなくブラウザです。

制限対象備考
256 MBpostMessage / ファイル読み込みこれより大きいものは読み込みを拒否し、悪意のある opener によるヒープ枯渇を防ぎます
32 MBXML および JSON コンバーターJS 側のガード（MAX_XML_BYTES / MAX_JSON_BYTES）と C++ ラッパー（kMaxXmlBytes / kMaxJsonBytes）の両方がこの上限を適用します。C++ 側は JS 側に依存せず単独で上限を保証します
XML エンティティ爆弾ガードXML コンバーター や 、または NUL バイトを含む XML は、libxml2 に渡る前に拒否されます。libxml2 自身のエンティティ展開制限も有効なので、これは billion laughs 型の入力に対する第二の防御層です
512 MBHDR タブのファイルファイルを読み始める前に、そのサイズで確認します。画像コーデック自身の 512 MB の入力上限と同じ値です
40 メガピクセル、1 バイトあたり 64 ピクセルRadiance HDR のデコード（HDR タブ）どちらもピクセル用のメモリを確保する前に、ヘッダーとファイルサイズから確認します。後者は反復マーカーによる展開爆弾を拒否します
EXR デコード予算OpenEXR のデコード幅 × 高さ × チャンネル数 × 4 バイトが 512 MB に収まる必要があり、デコーダーが何かを確保する前にヘッダーから確認します
HEIC/AVIF ボックス走査プロファイル抽出ボックスサイズはオーバーフローを起こさない方法で確認され、入れ子は 8 段、プロファイルは 64 MB（ファイルごとの合計）、アイテムの関連付けは 65 536 件が上限です
オリジン許可リストpostMessage による起動profiletool:load のバイト列を送信できるのは、同一オリジンと chardata の開発ホストのオリジンだけです
HTTPS + CORS#url= による起動URL 起動のプロファイルは、クロスオリジンの読み取りを許可するホストから HTTPS で配信されている必要があります。取得したバイト列はバリデーターにだけ渡され、再送信されることはありません

#url= による起動（1.1.5 で追加）は、ページ読み込み後にツールが別オリジンへのリクエストを行う唯一のケースです。指定されたプロファイルを取得できるよう、Content-Security-Policy の connect-src を https: に広げています。スクリプトの読み込み元は広げていません。広げているのはデータの取得だけです。

これらの制限を超えるプロファイルを検査する必要がある場合は、iccDEV をソースからビルドしてネイティブの CLI ツールを使ってください。それらには JS 側の上限はありません。

ICC.2 (iccMAX) の対応範囲

ICC.1 と ICC.2 の両方のプロファイルに対応していますが、ICC.2 への対応は不完全です。読み込み、ヘッダーとタグのビュー、検証、XML/JSON のラウンドトリップ、変換エンジンはいずれも ICC.2 を理解します。既知の不足は、マルチパートの ICS 交換ワークフロー、変換適用時の V5 サブプロファイルの選択、一部の ICC.2 プロファイルでの逆探索です。サポートされていない ICC.2 の構造を使うプロファイルは、誤って読み取られることなく、検証タブで報告されます。
